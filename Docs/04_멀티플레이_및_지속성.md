# 🏝️ 프로젝트 P.A. (Pioneer Assistance) - 멀티플레이 및 지속성

## 1. 네트워크 아키텍처 (Architecture)
[cite_start]프로젝트 P.A.는 별도의 대형 서버 유지비 없이 안정적인 멀티플레이를 제공하기 위해 **Host-Client** 모델을 채택합니다[cite: 44, 169].

### 1.1. 클라이언트-서버 모델 (UGS Relay)
* [cite_start]**네트워크 모델:** 사용자가 방장이 되어 자신의 섬을 서버로 개설하는 Host-Client 방식을 선택함[cite: 45, 169].
* [cite_start]**NAT 환경 극복:** 일반적인 가정용 인터넷의 보안(NAT) 문제를 해결하기 위해 **Unity Relay** 서비스를 활용하여 포트 포워딩 없이 안정적인 전 세계 연결을 보장함[cite: 55, 169].
* **역할 분담:**
    * [cite_start]**Host (Server):** 게임의 핵심 로직(NPC AI, 경제 재화 연산, 상점 재고)을 통제하며 데이터 소유권을 가짐[cite: 50, 51, 173].
    * [cite_start]**Client (Partner):** 섬의 '파견 파트너'로 참여하며 자신의 캐릭터 조작 정보만 전송하고 서버로부터 월드 업데이트 정보를 수신함[cite: 45, 54, 173].

## 2. 데이터 동기화 전략 (Sync Strategy)
[cite_start]Unity 6의 **Netcode for GameObjects (NGO)** 라이브러리를 활용하여 데이터의 일관성과 보안을 유지합니다[cite: 57].

### 2.1. 상태 동기화 (NetworkVariable)
* [cite_start]**용도:** NPC의 위치, 상점의 재고, 플레이어의 소지금 등 지속적인 상태 데이터를 실시간으로 공유함[cite: 62, 171].
* [cite_start]**권한 설정:** 보안 및 데이터 변조 방지를 위해 오직 서버(Host)만이 값을 수정할 수 있는 `WritePermission.Server` 권한을 부여함[cite: 64, 171].
* [cite_start]**UI 연동:** 값이 변할 때마다 `OnValueChanged` 이벤트를 발생시키는 **Observer 패턴**을 적용하여 클라이언트 UI를 자동 갱신함[cite: 65].

### 2.2. 상호작용 처리 (RPC - Remote Procedure Call)
* [cite_start]**ServerRPC (Client → Server):** 클라이언트가 자원을 채집하거나 물건을 구매할 때, 서버에 데이터 수정을 요청하는 상호작용 시작 단계에서 사용함[cite: 68, 171, 173].
* [cite_start]**ClientRPC (Server → Client):** 서버가 요청을 검증(좌표, 거리, 조건 등)한 후, 모든 플레이어에게 애니메이션 재생이나 시각적 효과를 명령할 때 사용함[cite: 69, 171, 173].

## 3. 멀티플레이 상호작용 시퀀스 (Interaction Sequence)
[cite_start]나무를 베는 상호작용을 예로 들어 데이터 검증 및 동기화 흐름을 정의합니다[cite: 173].
1. [cite_start]**Request:** 클라이언트가 도끼로 나무를 상호작용하여 `ServerRPC`를 호출함[cite: 77, 173].
2. [cite_start]**Validation:** 호스트는 해당 플레이어의 좌표에 실제 나무가 존재하는지, 상호작용 거리가 적당한지를 검증함[cite: 79, 173].
3. [cite_start]**Change:** 검증 통과 시 호스트는 해당 오브젝트의 상태를 변경(예: 내구도 감소)하고 `NetworkVariable`을 업데이트함[cite: 79, 173].
4. [cite_start]**Sync:** 호스트는 `ClientRPC`를 통해 모든 유저의 화면에 나무가 쓰러지는 애니메이션을 동시 재생하도록 명령함[cite: 78, 173].

## 4. 세션 지속성 및 권한 승계 (Persistence)
[cite_start]호스트 이탈 시 세션이 파괴되는 Listen 서버의 한계를 클라우드 기술로 극복합니다.

### 4.1. 클라우드 스냅샷 (UGS Cloud Save)
* [cite_start]**메커니즘:** 호스트는 게임 종료 또는 일정 주기마다 섬의 최신 상태(JSON 데이터)를 **Unity Gaming Services(UGS) Cloud Save** 저장소에 업로드함[cite: 202, 205].
* [cite_start]**영속성 확보:** 세션의 마지막 상태를 텍스트 형태로 보존하여 호스트의 기기 환경과 관계없이 데이터를 보존함[cite: 202, 205].

### 4.2. 권한 승계 (Authority Migration)
* [cite_start]**개념:** 기존 호스트가 부재중일 때 클라이언트가 플레이를 이어가길 원하면, 클라우드에서 최신 스냅샷을 내려받아 세션을 재개함[cite: 203].
* [cite_start]**지점장 대리:** 접속을 시도하는 클라이언트 중 권한을 부여받은 유저가 임시 호스트가 되어 월드를 로드하고 '지점장 대리'로서 경제 활동을 지속함[cite: 203, 205].
* [cite_start]**구현:** 별도 백엔드 구축 없이 유니티 계정과 연동되는 SDK를 활용하여 데이터 로드 및 호스트 선출 로직을 수행함[cite: 205].
