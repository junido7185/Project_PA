# Moonlighter — 낮의 준비가 밤의 판단이 되는 구조

근거: [S-ML1, S-ML2, R-04](SOURCE_REGISTER.md). P.A.는 낮에 생활/정착하고 밤에 영업한다. Moonlighter의 시간대·던전·전투·수동 계산대는 이식하지 않는다.

## ML-01 — 두 활동이 서로 다음 행동의 이유가 된다

- **D:** Digital Sun은 탐험 중 판매/제작을 생각하고 영업 중 다음 탐험의 구매·준비를 생각하는 두 핵심 활동의 연결을 설명했다(S-ML1). 금이 진행의 중심이어서 수입이 과하면 쉬워지고 부족하면 반복 노동이 된다는 균형 문제도 말했다(S-ML2).
- **I:** 각 모드를 따로 화려하게 만드는 것보다 이전 행동이 다음 판단의 자원이 되어야 루프가 결합된다.
- **P:** 같은 실제 ItemInstance/재고가 낮 획득 → 밤 진열·가격 → 고객 평가 → 확정 판매로 이어져야 한다. 완성 게임의 방향은 판매→주민 생활/마을 변화다. 데모는 Canon §16~21의 영업과 Pioneer Report까지 같은 사실을 보여준다. 새 재화·전투·던전·Day 2를 추가하지 않고, 돈만 유일한 성장 축으로 만들지도 않는다.
- **연결/완료 모습:** Inventory·ShopSlot·EconomyService·SalesLogManager 등 현재 권위. 구매/사용/가공의 장기 선택을 살리되 현재 가격 공식과 진행 조건은 승인 없이 변경하지 않는다.
- **다시 열 조건:** 낮의 수확이 영업과 단절, 영업 결과가 실제 재고/돈/기록과 불일치, 수입의 반복 노동 문제가 실제로 확인되거나 경제 변경이 승인됨.

## ML-02 — 가격 판단은 플레이어에게, 반응은 이해할 수 있게

- **O:** 기존 가격/고객 역분석은 가격 선택 → 고객 평가 → 반응/이동 → 구매 또는 거절을 구분했다(R-04). 원작의 정확한 확률·가격 공식은 확인하지 않았다.
- **I/P:** P.A. 플레이어는 상품과 가격을 정하고, 고객 성향과 실제 반응에서 배운다(Canon §17). 정답 추천가·구매확률·내부 평가식을 화면에 보여 판단을 대신하지 않는다. 반응은 가격/상태를 이해할 수 있는 플레이어 언어로 표현하고 내부 MBTI/reason key를 그대로 출력하지 않는다. 가격 창의 임시 입력·확정·취소를 구분해 취소가 실제 가격을 덮어쓰지 않게 한다.
- **연결/완료 모습:** ShopPriceUI·PurchaseEvaluator·기존 고객 presentation. 평가 권위를 UI에 복제하거나 UI 표시를 위해 무작위 구매 판정을 다시 실행하지 않는다. 튜닝 수치를 원작에서 추정해 현재 경제를 덮어쓰지 않는다.
- **다시 열 조건:** 가격 취소/확정 불일치, 내부 수치/디버그 문구 노출, 고객 반응으로 결과를 이해할 수 없는 실제 사례.

## ML-03 — 고객의 반응과 판매 확정을 같은 사건으로 취급하지 않는다

- **O:** 기존 역분석은 평가 말풍선·접근 행동·실제 거래를 서로 다른 단계로 분리했다(R-04). 이는 P.A.의 거래 경계를 설계하기 위한 구분이며 원작 코드 분석 결과가 아니다.
- **P:** 말풍선은 평가를, 판매 피드백은 기존 거래 commit을 표시한다. OPEN/CLOSE·재고 존재·가격/평가 상태·고객 접근을 현재 권위에서 확인한다. 재고 차감·돈 증가·SalesLog 기록은 기존 성공 경로에서 한 번씩 발생해야 한다. 실패/재고 없음/가득 참은 성공 연출로 가리지 않는다. 영업 종료 뒤 중복 구매나 남은 성공 피드백이 새 판매로 기록되지 않게 한다.
- **연결/완료 모습:** ShopSlot·PurchaseEvaluator·EconomyService·SalesLogManager·현재 NPC 고객 흐름. P.A.의 자율 구매를 플레이어의 수동 계산대 게임으로 바꾸지 않는다. 거래 완료 전에 성공 토스트/Report 수치를 낙관적으로 더하지 않는다.
- **다시 열 조건:** 말풍선만으로 매출 증가, 중복/누락 판매, CLOSE 뒤 구매, 판매 수량·돈·SalesLog가 서로 다름.
