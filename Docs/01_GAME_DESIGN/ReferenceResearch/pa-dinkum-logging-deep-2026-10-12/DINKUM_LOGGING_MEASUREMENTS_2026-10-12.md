# Dinkum 벌목 — 실측과 측정 방법

**측정 대상은 배포된 미디어 파일이다. Dinkum 엔진의 타이밍·충돌·입력 지연을 측정한 문서가 아니다.** 출처 ID와 장면 ID는 [근거 원장](DINKUM_LOGGING_EVIDENCE_LEDGER_2026-10-12.md)에 있다.

## 1. 파일 식별과 미디어 시간 M

영상 스트림 길이와 컨테이너 길이는 음향/패딩 때문에 다를 수 있다. 영상 프레임은 0 기반 n으로 식별하며, 실제 ffprobe의 `best_effort_timestamp_time`을 확인했다.

| 파일 ID | 파일 크기 | 영상 크기 | 평균 파일 FPS | 영상 프레임 수 | 영상 길이 / 컨테이너 길이 |
|---|---:|---|---|---:|---|
| DL-V01 | 10,185,663 bytes | 1920×1080 | 60/1 | 601 | 10.016667 / 10.026000초 |
| DL-V02 | 7,063,513 bytes | 2480×950 | 30000/1001 | 568 | 18.952267 / 18.952271초 |
| DL-V03 | 8,638,151 bytes | 1920×1080 | 60/1 | 540 | 9.000000 / 9.002000초 |

SHA-256:

```text
DL-V01 b3d436b5a44be6643af5eac73f71db24d99194d649a1c90ed56a98b91a72956f
DL-V02 3a4501cd2b4eb55259653f258e26625c1d02153932e43af978bb2a28b88915ed
DL-V03 8a1fe71e3491b8ba5c83f852ff2d9c90c737e42297fbc202352dfddaf4a50e75
```

V01은 time base `1/15360`, 시작 PTS=0이다. 확인한 프레임 간 PTS 차이는 256 ticks, 즉 1/60초다. `n/60` 계산값과 직접 추출한 PTS가 일치했다. 이 일치는 파일의 시간축을 설명할 뿐, 매 프레임 새로운 게임 simulation tick이나 애니메이션 pose가 생성됐다는 뜻이 아니다. 엔진 FPS·원본 캡처 FPS·중복/보간 프레임·편집 재생 속도는 판정하지 않았다.

## 2. 상세 관찰 구간과 표식

V01의 벌목 숏은 **n=284에서 시작, n=372까지 표시, n=373에서 다른 활동으로 컷 전환**한다. n=283에는 이전 용기 제시 컷이 남아 있다. 컷 전환 PTS 차이 `(373−284)/60 = 1.483333초`. 관찰 가능한 벌목 표시 프레임은 89개다.

먼저 V01 전체를 1초 간격으로 선별하고, 관련 구간을 약 0.2초 간격으로 확인했다. 상세 구간 n=282–380을 원래 프레임 순서로 추출했다. 단계는 3프레임 간격으로 비교했고, 컷 경계·되돌림 시작·두 효과의 판독 경계는 인접 프레임을 직접 대조했다. 확대/crop은 도구·발·줄기를 읽기 위한 분석용 보기였으며 시간축·프레임을 보간하지 않았다.

표식은 눈에 보이는 단계의 판독 기준이다. 특히 **‘원형 효과’와 ‘명확한 방사형 선’은 시각 분류 기준**이며, 별도 particle system이나 별도 내부 이벤트의 존재를 뜻하지 않는다.

| 표식 | n / PTS 초 | 바로 앞 비교 | 판독한 화면 O | 판독이 뜻하지 않는 것 |
|---|---|---|---|---|
| K-in | 284 / 4.733333 | n=283 이전 컷 | 도끼를 되돌려 든 벌목 구도로 전환 | 준비 동작 시작·입력 수락 |
| A-down | 290 / 4.833333 | n=289 | 첫 도구가 앞쪽으로 내려가는 자세 변화가 뚜렷해짐 | 첫 내부 swing event |
| A-line | 293 / 4.883333 | n=292 | 도구 주변의 밝은 선 | 실제 접촉·입력 비용 |
| A-ring | 294 / 4.900000 | n=293에는 이 원형 모양 없음 | 줄기 하부에 작은 원형 효과가 처음 확인됨 | 내부 hit commit |
| A-rays | 297 / 4.950000 | n=295–296 원형이 더 두드러짐 | 여러 방향의 밝은 직선이 뚜렷해짐 | 새 효과 이벤트 호출 |
| B-back | 328 / 5.466667 | n=327 낮은 앞쪽 자세 | 다음 되돌림으로 도구 각도가 달라지기 시작 | 두 번째 버튼 누름·버퍼 처리 |
| B-down | 342 / 5.700000 | n=341 되돌린 자세 | 두 번째 도구가 앞쪽으로 내려오는 변화 | 판정 가능 window 시작 |
| B-line | 345 / 5.750000 | n=344 | 도구 주변 밝은 선 | 실제 blade 접촉 |
| B-ring | 346 / 5.766667 | n=345에는 이 원형 모양 없음 | 두 번째 작은 원형 효과 | 자원 health 감소 |
| B-rays | 349 / 5.816667 | n=347–348 원형이 더 두드러짐 | 두 번째 방사형 밝은 선이 뚜렷해짐 | 자원 소진·아이템 생성 |
| K-last | 372 / 6.200000 | — | 나무가 선 채 벌목 숏 마지막 프레임 | 나무가 무한 자원이라는 규칙 |
| K-out | 373 / 6.216667 | n=372 | 채광 컷으로 전환 | 회복 종료·이동 해제 |

첫 되돌림의 시작은 컷 이전에 있을 수 있다. 따라서 첫 준비 시간은 측정하지 않는다. 발의 월드 좌표·미끄러짐 거리·도끼 궤적의 미터 단위·손 grip 오차·카메라 FOV/진동 크기 또한 측정하지 않았다.

## 3. 계산 가능한 간격 M

| 비교 | 계산 | 실제 보고값 | 사용할 수 있는 의미 |
|---|---|---|---|
| A-ring → B-ring | (346−294)/60 | **52프레임, 0.866667초** | 같은 숏에서 판독한 두 원형 효과 표식의 미디어 간격. 간격 표본 n=1 |
| A-line → B-line | (345−293)/60 | 52프레임, 0.866667초 | 두 도구 주변 선의 판독 표식도 같은 간격 |
| A-rays → B-rays | (349−297)/60 | 52프레임, 0.866667초 | 밝은 방사형 단계의 표식도 같은 간격 |
| A-ring → A-rays | (297−294)/60 | 3프레임, 0.050초 | 한 타격 표현에서 두 시각 판독 표식의 간격 |
| B-ring → B-rays | (349−346)/60 | 3프레임, 0.050초 | 두 번째도 같은 판독 간격. 내부 이벤트 간격은 U |
| B-back → B-ring | (346−328)/60 | 18프레임, 0.300초 | 화면에 드러나는 되돌림 시작 표식부터 원형 효과까지. **입력 지연 아님** |
| A-down → A-ring / B-down → B-ring | 각 4/60 | 각 0.066667초 | ‘뚜렷한 앞쪽 내려옴’ 표식부터 원형 표식까지. 실제 swing 전체 길이 아님 |

판독 시점과 실제 사건을 같게 두지 않는다. A-ring의 화면 전환은 마지막 부재 n=293과 첫 존재 n=294로, B-ring은 n=345/346으로 좁혔다. 그 사이의 연속적 시작을 추정하는 경우에만 약 **0.850–0.883333초**의 미디어 간격 범위를 쓸 수 있다. 더 정밀한 게임 사건 시점은 구하지 못한다. 흐릿한 효과/압축 때문에 ‘명확한 방사형 선’은 위 표의 시각 판독 기준에 의존한다.

세 표식이 52프레임 간격으로 반복됐다는 것은 이 숏의 **표현 위상 관계가 반복됨**을 지지한다. 홀드 자동 반복·입력 버퍼·애니메이션 고정 duration·게임 쿨다운·모든 도구의 속도·최적 손맛을 지지하지 않는다. 평균/분산/프레임 드롭/플레이어 만족도 통계는 계산하지 않았다.

## 4. 음향 파일의 실제 검사 M

‘video 요소가 muted’라는 이유만으로 원본 파일을 무음으로 판정하지 않았다. 세 파일에 각각 AAC 음향 스트림이 있었으므로 실제로 첫 음향 스트림을 float32 PCM으로 디코딩했다. 아래 수치는 채널을 합친 디코더 출력이며 패딩 샘플이 포함될 수 있다.

| 파일 | 디코딩 float 샘플 수 | 0이 아닌 샘플 수 | 절댓값 peak | RMS |
|---|---:|---:|---:|---:|
| DL-V01 | 962,560 | 0 | 0.0 | 0.0 |
| DL-V02 | 1,820,672 | 0 | 0.0 | 0.0 |
| DL-V03 | 864,256 | 0 | 0.0 | 0.0 |

결론: **확보한 세 배포 파일의 디코딩 음향은 전 구간 0이다.** 브라우저 음량을 올리거나 파형에서 peak를 찾는 방식으로 타격음·획득음을 복구할 수 없다. 원작 게임 자체가 무음이라는 의미는 아니다. 벌목 swish·contact·나무 쓰러짐·목재 착지·획득음의 존재, 음색, 상대 음량, 시작/잔향/중첩 시점은 모두 U다.

## 5. 재현 절차

원본 파일은 [근거 원장](DINKUM_LOGGING_EVIDENCE_LEDGER_2026-10-12.md)의 직접 URL에서 확보하고 SHA-256부터 비교한다. 해시가 다르면 같은 미디어라고 가정하지 않는다. 원작 파일을 P.A. 자산으로 가져오지 않는다.

다음 명령은 분석 절차의 예시다. `<file.mp4>` 자리에 직접 확보한 파일 경로를 넣는다.

```bash
ffprobe -v error -show_streams -show_format -of json '<file.mp4>'
ffprobe -v error -select_streams v:0 -show_frames \
  -show_entries frame=best_effort_timestamp,best_effort_timestamp_time,pkt_duration_time \
  -of json '<file.mp4>'
ffmpeg -i '<file.mp4>' -vf 'select=between(n\,282\,380)' \
  -fps_mode passthrough 'frame_%03d.png'
ffmpeg -v error -i '<file.mp4>' -map 0:a:0 -f f32le audio.f32
```

추출 연번 `frame_001.png`는 원본 n=282다. 파일 이름의 1 기반 연번을 원본 n으로 혼동하지 않는다. float32 데이터의 peak/RMS/nonzero는 Python 표준 `array('f')`로 계산했다. 음향 이벤트 명칭은 파형만으로 판정하지 않았고, 이번에는 샘플이 전부 0이어서 명칭/시점 판독 자체를 하지 않았다.

실제 게임 입력을 측정하려면 [추가 캡처 요구](DINKUM_LOGGING_CAPTURE_AND_GAPS_2026-10-12.md)에 따라 입력 표시·HUD·원본 음향이 들어 있는 동일 시간축의 연속 플레이를 새로 확보해야 한다.
