# 근거 방식, 단계 기록, 해석 규칙

## 목적과 산출물

‘비슷한 기능’보다 **플레이어가 원인과 결과를 읽고 다음 판단을 할 수 있는 조건**을 연구한다. 분석의 해상도는 이미지 크기가 아니라 입력·판단·상태·표현·실패를 구분하는 정밀도다. 접근한 공식 짧은 영상은 원본 해상도와 편집 제한을 그대로 기록한다. 고해상도 장시간 무편집 플레이 전체를 관찰했다고 주장하지 않는다.

## 근거 라벨

| 라벨 | 의미 | 허용되는 주장 | 금지되는 확대 |
|---|---|---|---|
| C | 확정 Canon/정체성 | 데모 계약 또는 장기 방향 | 오래된 재사용 맵으로 덮어쓰기 |
| V | 직접 확인한 영상의 시각 관찰 | 화면에 보이는 순서·형태·프롬프트 | 안 보이는 입력, 내부 상태, 음향, 반응 지연 |
| D | 공식 문헌 또는 제작자 발언 | 문헌이 설명한 규칙·개발 의도 | 영상에서 확인했다고 표현 |
| R | 저장소 코드·검증 기록 | 읽은 코드 경로, 기록된 검증 범위 | Unity에서 직접 재검증했다고 표현 |
| I | 설계 추론 | 왜 효과적일 수 있는지와 성립 조건 | 원작 개발자의 확정 의도 |
| H | P.A. 구현/검증 가설 | 기존 책임 위에 붙일 계약·실험 | 원작 내부 구현 또는 이미 적용된 변경 |
| U | 미확인 | 후속 관찰이 필요한 변수 | 임의 숫자·그럴듯한 단정 |

문서에서 ‘제안’, ‘권장’, ‘가설’, ‘품질 기준’으로 쓴 부분은 H/I이다. `ConsumeSuccess` 같은 실제 메서드의 설명은 R이다. 원작 버튼은 출처가 설명했거나 영상 프롬프트가 보일 때만 쓴다. P.A.의 E/WASD 등은 C이다.

## 실제 수행한 단계와 보존 위치

| 단계 | 수행 내용 | 보존 결과 | 완료의 뜻 |
|---|---|---|---|
| 1 경험 구조 | Canon·IDENTITY 원문, branch HEAD, 최신 상태·루프·재사용 기준 대조 | `00_basis/` | 데모 필수와 선택, 연구 우선순위를 고정 |
| 2 시스템 역분석 | 공식 Steam 미디어 8개 관찰, 공식 조작 문헌, 제작자 인터뷰·속편 개발 발언 대조 | `01_reverse_analysis/`, 장면/출처 원장 | 확인 가능한 근거 범위에서 행동·판단·표현을 분해 |
| 3 연결 원리 | 획득/소유권, 가격/관찰, 배치/동선, 정착/시간, 직접 노동/위임 연결 | 개발 자료의 시스템 계약 | 불변 조건·취소·경합·실패 사례로 전환 |
| 4 개발 지식 | 현재 코드 책임과 가설 대응, 자연 입력 품질 시나리오, 작업 단위·추가 촬영 계획 | `02_design_knowledge/`, 미확인 목록 | 다른 AI가 필요한 판단과 검증을 찾을 수 있음 |

단계 2의 ‘완료’는 모든 원작의 전체 플레이를 재현했다는 뜻이 아니다. ACNH는 공식 문헌 중심, Moonlighter 2는 버전별 문헌 중심이며 장시간 플레이 영상 검증은 미완료다. 이 한계를 구체적인 추가 촬영 단위로 보존한다.

## 영상 관찰 방법

공식 판매 페이지가 실제로 제공하는 DOM 미디어를 읽고, 재생 가능한 짧은 클립을 로컬로 내려받아 프레임을 추출했다. 타임스탬프는 **각 짧은 클립의 시작이 00:00인 파일 시간**이다. 원래 플레이 세션의 시각, 원작의 동작 지속시간, 엔진 FPS가 아니다. contact sheet 표본 사이의 순서는 보이지만 정확한 접촉 프레임·입력 지연은 측정하지 않았다. 마케팅 몽타주는 점프 컷을 명시한다.

8개 클립 모두 확인된 파일에 오디오 스트림이 없다. 따라서 소리 분석은 공식 문헌이 설명한 신호(D)와 P.A. 제안(H)을 구분한다. 원작의 실제 믹스·음압·타이밍은 U다. 원작 영상·추출 프레임·자산은 산출물에 포함하지 않는다.

Nintendo 공식 Treehouse 영상 페이지는 확인했으나 브라우저에서 재생이 멈췄다. 타임스탬프 분석의 근거로 쓰지 않았다. Dinkum의 메인 예고편은 화면상 재생 상태를 확인했으나 다운로드가 실패하여 체계적 장면 원장에 포함하지 않았다. 관찰 가능한 짧은 공식 클립과 문헌으로 작업을 이어갔다.

## 역분석에서 반드시 따지는 질문

하나의 동작마다 ‘대상이 먼저 읽히는가 → 행동 가능성을 판단할 수 있는가 → 입력이 수락됐는가 → 세계 작업이 성공했는가 → 보상이 실제 이전됐는가 → 다음 행동이 가능한가’를 분리한다. 애니메이션 성공과 경제 성공을 같은 것으로 취급하지 않는다. UI·카메라·사운드가 각 단계의 무엇을 설명하는지 따진다.

연출을 더할 때는 다음 반증을 함께 둔다. 장면을 보았어도 획득 물건을 모르면 획득 표현이 부족하다. 가격을 바꾼 이유를 말할 수 없으면 구매 결과의 정보가 부족하다. 자유 배치 후 손님이 오지 않으면 공간 자유의 계약이 부족하다. 제안은 이 반증을 통과하기 전까지 구현 가설로 유지한다.

## 숫자 사용 규칙

Canon의 8–12초 항해, 약 0.5초 Hold E, 25–35% 자원/내구도 여유, 10–20초 활동 간격, 12–15분 데모 목표는 C이며 실제 측정값이 아니다. 저장소의 20:00·21:30·22:00 등은 특정 데모 구현 설정 R이며 Canon 고정값이 아니다. 클립 길이/파일 FPS는 미디어 메타데이터다. 이외 타격 윈도·회전 속도·카메라 감쇠·UI 노출시간·원작 가격 임계값은 관찰 없이 정하지 않는다.

제안의 순서는 ‘애니메이션 준비 → 접촉 표현 → 결과 확인 → 회복’처럼 상대 순서로 정의한다. 수치 튜닝은 영상·입력·상태 로그를 함께 기록한 P.A. 플레이 실험으로 결정한다.
