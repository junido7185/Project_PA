# 실제 플레이 단위 설계 사례: 한 번의 행동을 끝까지 추적하기

이 문서의 장면은 **P.A. 구현·검수용 가설 H**다. 원작 영상에서 확인하지 못한 키·시간·내부 상태를 재구성한 것이 아니다. Canon의 입력과 기존 책임을 이용해 플레이어의 인식과 상태를 동시에 추적한다. 아래 상대 순서에 임의 초/프레임 값을 부여하지 않는다.

## 사례 A: 섬에서 도끼를 골라 첫 나무 작업을 한다

전제: 실제 Supply 지급 완료, 세계 조작 가능, 필수 목재를 더 얻어야 함. 도끼/목재 instance는 기존 Inventory에 있다. 원작 연결은 DK-01의 준비/시도/결과 구분과 AC-D1의 손 도구 문법이다. 나무 연속 타격의 원작 수치는 미확인(U-01).

| 플레이 단위 | 플레이어가 보고 판단하는 것 | 입력·실제 상태 H/C | 모션·카메라·UI·소리·환경 H |
|---|---|---|---|
| 자원 발견 | 숲의 나무와 접근 가능한 바닥을 보고 여기서 목재를 얻을 수 있다고 판단 | WASD/필요시 Space, 기존 이동·단차 판정 | 앞 지면/나무가 함께 보임, landmark 대비 유지. 아직 성공음 없음 |
| 도구 선택 | hotbar 도끼와 손 모델을 대조 | 숫자키, selected instance→held(C) | 선택 표시·손 socket/방향 일치, 도구가 몸 안에 묻히지 않음 |
| 문맥 확인 | 나무 앞 프롬프트가 작업을 가리키는지 봄 | 바닥 pickup이 있으면 그 후보가 우선(C) | 프롬프트가 실행 대상과 같음. 바닥 물건을 가리지 않음 |
| 시도 | 손과 도구가 대상 방향으로 움직여 입력 수락을 앎 | E, 시작 도구/대상을 연결, 중복 시작은 기존 gate | 준비→swing 표현, 시도 swish. 실제 성공을 먼저 알리지 않음 |
| 유효 작업 | 나무 반응을 보고 닿았다고 판단 | 기존 대상이 유효 작업 판정, 도끼 비용 −1(C) | 접촉점의 반응/음향. 재질/동작 방향 일치 |
| 보상 경계 | 나무 상태와 얻은/떨어진 목재를 읽음 | 실제 대상의 드롭형/직접 지급형 경로에 따름. 지급형은 실제 증가량 확인 | 드롭과 가방 획득이 다른 사실이면 다른 표현. 아직 미획득 드롭에 획득 완료음 금지 |
| 다음 행동 | 더 작업하거나 바닥 물건을 줍거나 이동을 선택 | 회복/다음 E, 이미 처리한 결과 재지급 금지 | 과도한 카메라 이탈·장기 결과 잠금 없이 다음 대상이 읽힘 |

실패 분기: 허공은 swing만, 잘못된 자원은 맞지 않는 접촉의 짧은 반응, 둘 다 비용 0(C). 가방 부족은 실제 지급 실패이며 ‘획득’을 표시하지 않는다. 도구 변경이 작업 중 허용된다면 시작 도구로 완료 또는 취소하는 일관된 정책을 쓴다. X 뒤에는 선택 도끼가 남아도 손이 빈 상태다.

검수 질문: 플레이어가 ‘E가 먹었는가’, ‘닿았는가’, ‘목재를 가방에 받았는가’를 각각 말할 수 있는가? 도구 비용과 물건 수량의 로그가 그 설명을 지지하는가? Q-A01–04/Q-V01.

## 사례 B: 고객이 상품을 구경하는 동안 가격을 바꾼다

전제: OPEN, 가판대에 실제 판매품, 고객은 기존 Browse 경로로 접근. 원작 연결 ML-01–05. **현재 P.A. Evaluate→purchase는 같은 메서드에서 동기 실행**하므로 그 사이에 수동 입력할 수 있는 가상의 긴 단계를 만들지 않는다.

| 플레이 단위 | 플레이어의 관찰·판단 | 상태·소유자 H/R | 표현/환경 H |
|---|---|---|---|
| 상품 확인 | 내 상품·수량·가격을 봄 | ShopSlot 실제 currentItem/displayPrice | 가판대 모델/가격은 같은 상품, warm night 조명에서도 읽힘 |
| 고객 접근 | 어느 상품에 관심 있는지 따라봄 | NpcController 접근/browse, 기존 approach 예약 | 이동/바라보는 방향과 상품이 연결. 다른 가판대 bubble로 오인하지 않음 |
| 가격창 열기 | 조금 조정할 이유를 정함 | E→기존 ShopPriceUI, 세계 E 차단 | 현재값·편집값·확정/회수 의미가 보임. 뒤의 세계 프롬프트가 혼동을 만들지 않음 |
| 값 편집 | 바꾼 숫자를 읽음 | Drag/±, `_pendingPrice`만 변화(R) | 운영 가격은 확정 전 그대로. UI 입력음은 sale 완료음과 구별 |
| 확정 | 새 조건을 손님에게 제시 | OnConfirm→ShopSlot display→OnPriceConfirmed(R) | 상품 표시에 운영값 반영. 같은 입력이 세계에 재전달되지 않음 |
| 평가/실제 판매 | 특정 고객의 결과를 읽음 | claim→Evaluate→기존 TryPurchaseByNpc(R) | 결정의 표정/문구와 commit의 money/품절 신호를 구분 |
| 다음 판단 | 반응을 보고 유지/다시 조정/다른 상품 선택 | 새로운 고객/평가 결과를 기다림 | 단일 거절로 ‘가격 정답 아님’을 확정하지 않도록 설명 가능한 표현 |

가격 확정이 평가보다 앞서면 새 가격, 평가/판매 이후면 기존 거래 가격이 기준이다(H). 현재 동기 경계에 지연 연출을 넣는다면 slot 잠금 또는 quote 유효성 계약을 먼저 설계한다. 구매 의향은 true였지만 서비스/gate/stock 문제로 commit 실패했다면 판매 성공 효과·보고서 매출이 생기면 안 된다.

고품질 상품의 같은 basePrice 비교만으로 ‘비싸다’고 표현하면 quality 보정 Evaluate와 기준이 다를 수 있다(R/H). 고객의 최종 거절은 취향/가격/무작위성의 결합이므로 실제 price perception의 정책 없이 원인 하나로 설명하지 않는다. Q-C02–05/Q-V03.

## 사례 C: Workbench를 옮기려다 취소한다

전제: CLOSED, 빈손, 실제 Workbench instance가 놓여 있음. Workbench는 건물이 아닌 오브젝트(C). 원작 배치 preview 세부 영상은 U-06이며 아래는 P.A. 기존 서비스 R에 대한 계약이다.

| 플레이 단위 | 플레이어의 관찰·판단 | 상태·소유자 H/R | 표현/환경 H |
|---|---|---|---|
| 대상 앞 | 제작과 이동이 가능한 같은 Workbench임을 앎 | PlayerInteraction 후보/빈손 | tap/hold가 구별되는 현재 맥락 안내 |
| E 누르기 | 이번에는 제작보다 이동을 의도 | pendingHold 시작(R) | 시작 즉시 제작창을 열어 hold를 방해하지 않음 |
| Hold 통과 | 물건을 집어 이동 모드로 들어갔다고 읽음 | Canon 약 0.5초, BeginMove 경로 1회 | 이동 ghost/모드 표현, held kit 복제 없음 |
| 위치·회전 | 원하는 방향/입구·영역을 예측 | WASD/R, placement preview 검사 | ghost 실제 규모, 허용 영역/여백과 valid/invalid 이유 |
| 불가능한 위치 | 문/통행을 막는다고 앎 | 기존 failure, 실제 object/재고 아직 확정 변경 없음 | 막힌 공간을 읽히게 함. 실패 확정음 금지 |
| 취소 | 원래 상태로 돌아가기로 결정 | Esc/RMB→CancelPreview, 복원 성공 여부 확인 | 원본 위치/방향/활성 복귀, ghost·모드 정리 |
| 재사용 | 같은 Workbench로 다시 제작 | 새 tap E, 정상 UI owner | 원래 제작/사용 접근 유지, 잔류 hold로 다시 이동하지 않음 |

원본 점유를 해제하는 이동 모드에서 복원 실패 시 서비스는 원본/예약/preview를 유지하고 false를 반환한다(R). caller는 취소 성공처럼 UI를 닫고 끝내지 않는다(H). 복원이 성공할 때까지 명료한 재시도 상태를 남긴다. 취소는 새 kit 지급도, 기존 object 삭제도 아니다.

같은 순간 OPEN이 요청되면 실제 preview/복원 상태를 먼저 해결하거나 개점을 거절하는 기존 gate 정책이 필요하다(H). 손님이 숨겨진 원본과 끊긴 동선을 가진 채 들어오는 상태를 만들지 않는다. Q-A05/Q-P03–04/Q-V02.

## 세 사례를 함께 검증하면 드러나는 연결 원리

같은 E는 **현재 의도·손·대상·모드**에 따라 의미가 달라진다. 같은 성공 표현은 **실제 책임의 결과**를 받아야 한다. 같은 취소는 **입력뿐 아니라 물건·점유·UI·다음 행동**을 복구해야 한다. 이 관계가 일치하면 새로운 물건/활동에도 기존 문법이 전이된다. 불일치하면 새 시스템을 더 추가할수록 학습 비용과 버그가 늘어난다(I/H).
