# PRE-01/Q: 표현의 의미와 구현 후 플레이 품질

Canon §1.3·§19–20·§22–25. 이 문서의 시나리오는 수행할 검수 H이며 이번 연구가 실제 게임을 실행해 얻은 결과가 아니다. 원작 근거는 [Dinkum](../01_reverse_analysis/01_DINKUM_ACTION_AND_WORLD.md), [Moonlighter](../01_reverse_analysis/03_MOONLIGHTER_COMMERCE.md), [Dave](../01_reverse_analysis/04_DAVE_LOOP_AND_CINEMATIC.md).

## 표현이 알려주는 사실을 먼저 정한다

| 실제 사실의 출처 | 애니메이션·환경 H | UI H | 사운드 H | 잘못된 피드백 |
|---|---|---|---|---|
| 행동이 수락됨 | 손/몸의 준비·방향 | 필요할 때 현재 행동 | swish 등 시도 신호 | 수락 안 됐는데 성공 표정 |
| 유효 접촉/세계 작업 | 대상별 흔들림·입자·드롭 | 짧은 맥락 안내 | 접촉 재질 신호 | 허공에서 나무 contact 음 |
| Inventory 지급 성공 | 획득 물건 표시 | 실제 item·증가량/선택 변화 | 획득 완료 신호 | 가방 실패인데 보상 toast |
| 가격 확정 | 상품/가격 표시 갱신 | 확정값과 pending 분리 | UI 확정 신호 | pending을 운영 가격처럼 표시 |
| 고객 판단 | 대상 쪽 시선·짧은 반응 | 설명 가능한 가격 인식/결과 | 판단 신호는 판매와 구별 | 모든 거절을 과가격으로 단정 |
| 판매 commit 성공 | 해당 진열 수량/품절 | 통화·기존 판매 기록 | 거래 완료 신호 | 의향만으로 돈 효과 |
| CLOSE/정산 완료 | 밤 활동 종료/주민 복귀 | 실제 보고서/다음 접근 | 하루 마감 신호 | 남은 callback이 보고서 뒤 판매 |

원작의 소리는 무음 clip에서 확인하지 않았다. 위 소리의 종류는 기능 의미 제안이며 원작 음원/믹스 복제가 아니다. 기존 음량 설정·SFX pool에서 실행한다.

## 행동의 질은 다섯 구역을 함께 본다

H: 도구 손잡이와 손, 발과 지면, 도구 궤적과 대상, 시야와 다음 행동, 결과 UI와 실제 물건이 일치해야 한다. 손맛은 애니메이션만의 문제가 아니다. 모델 scale·socket·pivot이 틀리면 시간을 조절해도 접촉이 틀려 보인다. 카메라가 발/대상을 가리면 동작이 자연스러워도 판단이 어렵다.

현재 기록은 grip 기능 PASS와 시각 FAIL, foot contact 미해결을 분리한다(R). 따라서 ‘도구가 손에 나타난다’는 검사 이후에 grip 접촉·회전·정지·swing recovery를 사람 시점으로 검수한다. 보행, 점프 착지, 실패 swing, 획득 직후, 빈손 전환에서 동일한 몸/도구 관계를 본다.

## 카메라 튜닝의 목적

현재 `CameraController`에는 같은 follow 권위 안의 opening/build framing·충돌 보정·LateUpdate 경로가 있다(R). H: 튜닝은 다음 네 판단을 보호한다. 다음 지면을 어디로 밟나. 어느 대상에 E를 하나. ghost가 실제 놓일 위치는 어디인가. 손님이 어떤 상품에 반응했나.

가림 회피를 빠르게 하는 것만으로 해결되지 않는다. 나무 때문에 카메라가 들어오며 도구·상품·문이 잘리는지, 가림이 해제될 때 목표물이 갑자기 작아지는지, build framing에서 돌아올 때 입력/타깃이 안정되는지 실제 경로에서 본다. 원작 FOV·damping·collision radius 측정값은 없다. 기존 P.A. 설정을 기준선으로 저장하고 한 변수씩 조절한다.

## UI의 최소 계약

C: 잠깐의 맥락 안내, 놓친 알림의 Phone 기록, 내부 가격 정답/확률 없음, 낮 동안 demo 점수 HUD 없음. H: interaction prompt·toast·dialog·modal·report는 각각 무엇이 입력을 받고 무엇이 배경 정보인지 읽혀야 한다. modal의 뒤에 세계 행동 안내가 겹쳐 떠 있으면 입력 기대가 깨진다.

현재 tooltip의 Space 문구, 대화/힌트 겹침, NPC 말풍선 검수 미완료가 보고된다(R). 개별 텍스트 수정만으로 끝내지 않고 실제 owner와 문구를 같은 기준으로 갱신한다. 1080p뿐 아니라 현재 검증에 사용했던 720p/좁은 화면에서도 item·가격·확정/회수 버튼·길 안내의 우선순위를 확인한다. 이는 특정 원작의 UI 배치를 복제하는 작업이 아니다.

## 항해와 도착의 계약

C: 8–12초 픽셀 항해, 권장 쇼트는 출항→파도/배/동행→섬 실루엣→확대→Fade/3D. 하선 완료·배 landmark·Day 1은 조작 시작부터다.

H: 마지막 전환 전에 플레이어/NPC 2명·카메라·UI·clock 상태가 준비되고, 이후 입력을 한 번 열어준다. 전환 때 눌린 E/Space가 새 세계 행동으로 새지 않게 한다. 바다 배 방향과 섬 도착 landmark의 방향을 연결하면 공간을 기억하기 쉽다. 원작의 픽셀 캐릭터·파도·과장 이펙트를 복제하지 않고 P.A. 인물/항구로 구성한다. 쇼트별 임의 timing은 이 연구에서 지정하지 않는다.

## 보고서는 하루의 사실을 확인한다

C: Report는 demo only, CLOSE 후 공개. 초기 평가 영역 가중치는 25/30/25/20, S/A/B/C의 초기 기준은 90/75/60이며 C도 실패가 아니다. rule-based 댓글 2–4개, LLM 실시간 생성 없음. 고정값은 Canon의 초기 tuning 기준이다.

H: 댓글은 ‘조건 → 실제 기록 → 문장’으로 연결한다. 판매 없는데 ‘대박 매출’ 문구, 선택하지 않은 분야 칭찬, 하지 않은 fish catch 언급을 하지 않는다. 선택 활동을 하지 않은 플레이어에게 다음 행동의 흥미를 남길 수 있지만 필수 실패로 평가하지 않는다. 같은 정산을 두 번 열어도 rank·매출·사건은 바뀌지 않는다. Report 닫기에서 Phone/세계 입력으로 정상 복귀한다.

| 묶음 | 조건·촬영 범위 H | 기능 판정과 별도로 사람이 답할 질문 |

12–15분은 Canon Pass3 목표다. 실제 관찰한 데모 길이로 쓰지 않는다. 시간 목표를 맞추려고 자원·배치·거래를 fixture로 건너뛰면 자연 완주 증거가 아니다.

## 기록할 측정값과 해석

H: 입력→표현 시작, 유효 작업→실제 보상, 목표를 보는 데 걸린 시간, 잘못 누른/되돌아간 횟수, 가격 수정 전후 관찰, 문 앞/가판대 접근 실패를 같은 영상·이벤트 로그에서 기록한다. 임의 합격 latency 수치를 설정하지 않는다. 먼저 명료성 실패를 찾아 원인을 고친 뒤 기준선을 정한다. 평균만 보고 반복마다 다른 실패를 숨기지 않는다.

사람 품질 기록에는 ‘좋음’ 대신 장면과 문제를 쓴다. 예: ‘벌레를 향해 E를 눌렀지만 대상이 화면 밖에 있어 허공인지 실패인지 몰랐다’. 이 경우 첫 수정 대상은 reward 수치보다 camera/target cue다. 결함을 기능·읽기·회복 중 어디에 속하는지 쓰면 다음 AI가 올바른 영역을 수정할 수 있다.
