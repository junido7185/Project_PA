# Moonlighter: 가격 판단을 손님의 행동으로 되돌려주는 상점

연구 대상 COM-01. Canon §11·§16–18·§20·§23. 시각 근거 ML-01–05, 문헌 ML-D1·ML2-D1·ML2-D2. 1편의 짧은 공식 clip과 2편의 버전별 발언을 합쳐 하나의 ‘원작 규칙’으로 쓰지 않는다.

## 확인한 상점의 작은 사건

ML-V1에는 상품별 숫자 말풍선, 상품 가까이의 웃는 표정, 물건을 든 고객의 이동, 계산대의 `A Sell` 프롬프트가 보인다(V). 클립은 HUD가 잘렸고 무음이다. 거절·가격 Drag·돈 증가·정확한 버튼 입력은 확인하지 못했다(U). 따라서 ‘고객이 사라졌다 = 경제 commit 성공’이라고 판정하지 않는다.

아래는 보인 사건을 기능 목록이 아니라 판단의 경계로 읽는 분석이다(I).

| 경계 | 플레이어가 보는 V | 판단을 가능하게 하는 관계 I | P.A.에서 필요한 상태 H |
|---|---|---|---|
| 상품 제시 | 상품과 가격이 공간에서 가까움 | 가격이 어떤 물건의 조건인지 안다 | 상품 identity·품질·수량·가격 버전 |
| 고객 관찰 | 물건 가까운 고객 위의 표정 | 특정 고객이 특정 조건에 반응했음을 연결한다 | 평가 대상·평가 시 가격·한 번의 평가 결과 |
| 구매 의향 이후 | 고객이 물건을 들고 계산대 방향 이동 | 구매 판단과 거래 완료 사이의 진행을 읽는다 | claim·접근/이동·취소 가능성 |
| 거래 접점 | 플레이어 근처 `A Sell` | 다음 행동 장소를 안다 | 실제 기존 판매 commit, 중복 방지 |
| 반복 | 다른 고객이 비슷한 경로 이동 | 여러 반응을 비교할 기회가 생긴다 | 신규 평가와 기존 결과를 구별 |

표의 오른쪽 상태는 원작 코드가 아니라 P.A. 설계 가설이다. 원작의 수동 계산대 입력을 P.A. 필수로 추가할 이유는 없다. Canon/현재 구현은 기존 자율 판매 경로를 사용한다. 가져올 원리는 **상품의 조건 → 고객 판단 → 이동 → 경제 결과의 순서가 읽힌다**는 점이다.

## 가격은 숫자 조절 기능보다 작은 실험이다

가격 실험이 의미 있으려면 플레이어가 독립 변수를 알고, 반응을 식별하고, 재시도할 여지가 있어야 한다(I). Drag를 붙이는 것만으로 이 조건이 생기지 않는다.

첫째, 가격창에서 수정 중인 값과 확정된 값의 차이가 읽혀야 한다. 둘째, 고객이 보던 가격이 수정됐다면 어느 값을 평가한 것인지 일관돼야 한다. 셋째, 구매 실패와 접근 실패가 같은 표정이면 가격 실험에 공간 문제가 섞인다. 넷째, 다른 성격의 고객이 섞이는 게임이라면 단일 반응을 상품 전체의 정답으로 해석하게 만들면 안 된다.

P.A.의 현재 `PurchaseEvaluator`는 가격·품질·카테고리·NPC 성향과 RNG를 결합한다(R). 이것은 원작의 정확한 가격 공식을 확인했다는 뜻이 아니다. P.A.는 한 번의 거절로 ‘가격이 틀렸음’을 확정할 수 없는 구조다. 따라서 ‘거절했으니 비싸다’만 출력하는 설명은 경험과 모델을 어긋나게 할 수 있다(H).

## 학습 가능한 반응의 조건

| 문제 | 결과 | 제안 H |
|---|---|---|
| 말풍선이 여러 고객/가판대 사이에 떠 있음 | 어떤 상품의 반응인지 모름 | 평가 대상 근처 또는 시선·짧은 연결로 source를 읽게 함 |
| 랜덤 거절마다 같은 과가격 문구 | 합리적인 가격도 잘못됐다고 학습 | 가격 인식과 실제 구매 결과를 분리해 설명 가능한 반응만 표시 |
| 가격 수정 직후 예전 고객의 반응 | 수정 효과가 없거나 역효과처럼 보임 | 평가/거래 가격 버전 유지, 기존 고객과 새 평가 구분 |
| 돈 효과가 먼저 나고 실패 처리 | 판매 사실을 믿을 수 없음 | 기존 commit 성공을 확인한 뒤 경제 연출·보고서 이벤트 |
| 매번 정답가/확률 제공 | 관찰과 판단의 가치가 사라짐 | Canon처럼 내부 확률·추천가 숨김, 실제 반응을 참조 |
| 첫 밤 고객 표본이 너무 적거나 모두 같은 성향 | 플레이어가 조정의 이유를 얻기 어려움 | 첫 밤의 관찰 기회를 검증하되 결과 강제/계산식 교체는 별도 설계 판단 |

이 제안은 새로운 가격 판정 엔진을 만들라는 뜻이 아니다. 기존 Evaluate/판매 권위 위에 표시 정보와 사건의 출처를 맞춘다. `Result.reason`은 현재 debug 문자열이며 그대로 플레이어 문구로 노출하지 않는다.

## Moonlighter 2가 주는 버전별 교훈

ML2-D1에서 개발자는 1편의 가격 추측이 처음에는 재미있지만 해결 후 반복이 되고 자동 상점 기능으로 넘어간다는 문제를 설명했다. 당시 2편 데모는 가격을 매번 추측하기보다 perk·장식·상품 조합으로 판매 가치를 높이는 방향을 설명했고, 상점 주도권/무작위성 피드백을 받아 혼합 접근을 검토했다(D, 2025-06).

이것을 ‘2편은 가격을 정하지 않는다’는 현재 규칙으로 쓰면 안 된다. ML2-D2는 2026-05 이후 상점 행동 변경과 이후 1.0 공지를 확인시킨다(D). 이번 연구는 1.0 가격창·구간 지표·현재 상점의 연속 플레이를 직접 검증하지 못했다. 구체적인 최신 가격 규칙의 이전은 보류한다.

P.A.에 유용한 교훈은 두 단계다(I). 첫 밤은 아직 모르는 상품과 고객에 대해 작은 가격 결정을 배우는 시간이므로 직접 책정이 중심이다. 장기에는 플레이어가 이미 알아낸 규칙을 계속 재발견하게 만드는 반복을 피할 필요가 있다. 그러나 현재 데모에서 perk·상점 빌드·assistant·카드식 증폭을 추가하는 것은 범위 밖이다. 기존 판매 기록의 해석과 소유감부터 완성한다.

## 상점 공간은 학습 도구다

상품을 보는 위치와 반응을 보는 위치가 가깝고, 구매 이동이 이어지면 플레이어는 같은 사건을 추적한다(I). P.A.의 3개 독립 가판대에서는 출입구·관찰 위치·판매 동선이 교차하며 표현을 가릴 수 있다. 입구에서 고객이 어디로 가는지, 가격을 본 순간이 언제인지, 돈이 왜 늘었는지를 움직임만으로 따라갈 수 있는지 검사한다(H).

OPEN 중 가판대/가구 이동 금지는 자유를 줄이는 임의 제약이 아니라 이미 약속된 고객의 경로·평가를 안정시키는 규칙으로 설명할 수 있다(I, C §11.3·§16). 가격 수정은 허용되지만 평가 중 해당 가판대만 잠시 잠그는 방식도 Canon이 허용한다. 전체 상점을 UI 때문에 멈추는 접근보다 기존 고객과 입력을 어떻게 조정할지 먼저 정한다.

## 구현 판단으로 넘어가기

[상점 개발 지식](../02_design_knowledge/03_COMMERCE_PRICE_CUSTOMER.md)은 quote·claim·commit·취소·CLOSE의 관계와 실제 코드 검토 위험을 다룬다. 원작의 행복/거절 아이콘, 상품 스프라이트, 가격표, 상점 레이아웃을 복제하지 않는다. 고객의 판단이 플레이어의 다음 결정에 쓸 수 있는 사실이 되도록 P.A. 표현을 새로 설계한다.
