## 3. 구현 과정의 주요 도전과 해결

### 도전 1 — 아이템에 품질과 가격을 저장할 수 없음

**요구사항 (명세서 §7-B):** 아이템별 품질(quality), 개별 가격, 고유 ID 보존  
**발생 상황 (세션 7까지):** 인벤토리 슬롯이 `Item`(ScriptableObject 원형)을 직접 참조 → 품질·가격 정보 저장 구조 자체가 없었음

```
[문제]  InventorySlot → Item(SO)  // quality, price 필드 없음
[결과]  진열대에 올려도 모든 아이템이 품질 1.0 고정
        PurchaseEvaluator의 부가가치 수식이 항상 동일하게 동작
```

**해결 (세션 8):** Item / ItemInstance 레이어 분리

```
Item (ScriptableObject)  — 정적 원형, 씬 전체 공유
ItemInstance             — 런타임 동적 상태 (quality, currentPrice, GUID)
InventorySlot            — ItemInstance를 래핑, 기존 코드 호환 accessor 유지
```

하위 호환을 위해 `slot.item` → `instance.data`, `slot.count` → `instance.count`로 읽히도록 설계해 **기존 호출 코드를 수정하지 않고** 마이그레이션 완료.  
드래그 앤 드롭 교환도 참조 스왑(`SetInstance`)으로 처리해 품질 정보 유실 0.

### 도전 2 — 재화 변경 경로가 코드베이스 곳곳에 흩어짐

**요구사항 (명세서 §1-B):** EconomyService — 모든 재화 변경의 단일 경로  
**발생 상황 (세션 8 이전):**

```
GameManager.money += price     // 방법 1
GameManager.AddMoney(-cost)    // 방법 2
직접 대입                       // 방법 3
```

차감 실패를 확인하지 않고 `AddMoney(-price)`를 무조건 호출하는 패턴 → 잔액 부족 시에도 돈이 차감되는 버그 발생.

**해결 (세션 8):** `EconomyService.TrySpend(amount)` 단일 원자적 호출

```csharp
// 잔액 확인 + 차감이 한 번에 처리됨 (실패 시 차감 없음)
if (!EconomyService.Instance.TrySpend(buildCost, "건물건설")) return;
Instantiate(buildingPrefab, pos, rot);
```

부수 효과: `_money` 필드를 `NetworkVariable<int>`로 교체하면 멀티플레이 공유 지갑으로 즉시 전환 가능 — 졸업 이후 확장을 미리 설계에 반영.

### 도전 3 — 저장 백엔드 교체가 불가능한 강결합 구조

**발생 상황 (세션 4 초기):** `SaveManager`가 `File.WriteAllText(path, json)` 직접 호출 → Cloud Save로 전환 시 SaveManager 전체를 재작성해야 하는 구조

interface ISaveRepository {

// 현재 구현체: LocalJsonSaveRepository
// 향후 교체:  UGSCloudSaveRepository  ← SaveManager 코드 무수정

### 도전 4 — NPC 구매 로직이 테스트·검증 불가능한 구조

**요구사항 (명세서 §1-F):** NPC 구매 결정 — MBTI 4축 × 가격비율 × 품질  
**발생 상황:** 구매 로직을 `NpcController.Update()` 안에 직접 구현하면 외부 상태(Shop, UI 등)에 의존 → 단위 테스트 불가, 결과 재현 불가

**해결 (세션 8):** `PurchaseEvaluator.Evaluate(profile, slot, rng)` 순수 함수 분리

```
구매 확률 계산:
  1. idealPrice  = basePrice × (1 + 0.5 × max(0, quality-1))   ← 품질 부가가치
  2. ratio       = displayPrice / idealPrice
  3. baseProb    : ratio≤0.7 → 95%, ratio=1.0 → 70%, ratio≥1.5 → 5%
  4. 카테고리 보너스 (S/N 축 × 아이템 카테고리 매칭)
  5. T/F 축 보너스 증폭 ±15%, 가격민감도 ±10%
  6. E/I 축 충동 구매 ±10%
  7. finalProb   = clamp(baseProb + bonus - penalty, 0, 1)
  8. rng.NextDouble() < finalProb → 구매
```

`UnityEngine.Random` 전면 제거 → NPC별 `System.Random` 인스턴스(고정 시드) 사용.  
동일 시드이면 항상 같은 구매 패턴 → 디버그 재현 가능, 멀티플레이 서버 검증 친화적.

### 도전 5 — 가공해도 품질이 항상 1.0으로 나옴

**요구사항 (명세서 §1-H):** CraftingService — 재료 품질 가중평균 → 결과물 품질 반영  
**발생 상황 (세션 9 이전):**

```
CraftingUI → Inventory.AddItem(Item, int)  // 품질 메타 없이 기본값으로 생성
→ PurchaseEvaluator가 항상 quality=1.0을 받음
→ 부가가치 루프 0% 작동
```

**해결 (세션 9, 11):**

```csharp
// CraftingService.TryCraft()
float avgQuality = Inventory.GetAverageQuality(recipe, rng);
float outputQuality = recipe.baseOutputQuality
                    + recipe.ingredientQualityWeight * (avgQuality - 1f);
var result = new ItemInstance(recipe.outputItem, 1, outputQuality);
Inventory.AddInstance(result);  // 품질 메타 보존 경로
```

`GetAverageQuality`는 실제로 차감될 스택과 동일한 탐색 순서(핫바→인벤토리)를 사용해  
"차감되는 재료의 평균 품질"을 정확히 계산. → 역-공급망 품질 부가가치 루프 완성.

### 도전 6 — NPC가 24시간 내내 쇼핑만 하거나 생산만 함

**요구사항 (명세서 §1-F + Docs/03 §1.2):** NPC 기상→작업→쇼핑→귀가 일과 흐름  
**발생 상황 (세션 10 이전):** NpcController(소비형)와 ProducerNpcController(생산형)가 각자 독립 FSM으로 24시간 동작. J/P 축이 NpcProfile에 존재하지만 실제 연산에 전혀 미반영.

**해결 (세션 10):** `GameClock` + `NpcDailySchedule` + `NpcScheduleController` 3단계 구조

```
GameClock.OnHourTick
    → NpcScheduleController.EvaluateAndApply(currentHour)
        → NpcDailySchedule.GetPhaseAt(hour)  ← ScriptableObject로 기획자가 편집
            → Work    : producerController.Resume()
            → Shopping: consumerController.SetShoppingPriority(true)
            → Sleep   : 전체 Pause() + ReturnHome()

J/P drift:
    P형(+1): 30% 확률로 스케줄 이탈 → 즉흥 쇼핑
    J형(-1): 이탈 0%, 스케줄 엄격 준수
```

NpcDailySchedule을 ScriptableObject로 만들어 **코드 수정 없이** Inspector에서 일과 편집 가능.

### 도전 7 — 건물 실내 진입 씬 구조 선택

**요구사항 (명세서 §1-J):** 건물 내부 진입·퇴장 전환  
**검토한 3가지 방법:**

| 방식 | 장점 | 단점 |
|---|---|---|
| Additive Scene | 씬 독립, 정리된 구조 | NavMesh 분리, 싱글톤 상태 단절 |
| 완전 씬 전환 | 가장 단순 | 로딩 시간, 상태 재초기화 필요 |
| **단일 씬 Y+100 오프셋** | NavMesh 공유, 싱글톤 연속, 쾌적한 진입감 | 씬 y축 정리 필요 |

**결정:** Y=+100 오프셋 방식 채택 (Stardew Valley, Moonlighter 2 동일 방식)

구현 과정에서 마주친 추가 버그:
- `CharacterController.transform.position` 직접 대입 시 내부 누적이동이 다음 프레임에 덮어써 텔레포트가 취소되는 버그  
  → `cc.enabled = false → 위치 대입 → cc.enabled = true` 순서로 해결
- 카메라 `Lerp(smoothSpeed=5)`가 Y+100 이동을 수 초간 패닝으로 보여주는 문제  
  → `CameraController.SnapToTarget()` 추가로 텔레포트 프레임에 즉시 스냅

### 도전 8 — UI 위치가 해상도마다 달라지는 문제

**요구사항 (명세서 §6):** SmartphoneUI — 화면 중앙 팝업  
**발생 상황:** `activePos = (770, 200)` 하드코딩 → 1920×1080에서만 중앙, Free Aspect에서 엉뚱한 위치

**해결:** `SmartphoneUI.ComputeActivePos()` — Toggle 시 캔버스 실제 rect를 읽어 동적 계산

```csharp
Vector2 ComputeActivePos() {
    var rect = _canvas.GetComponent<RectTransform>().rect;
    return new Vector2(rect.width * 0.5f - _rt.rect.width * 0.5f,
                       rect.height * 0.5f - _rt.rect.height * 0.5f);
}
```

CanvasScaler `Scale With Screen Size + matchWidthOrHeight=0.5` 환경에서는 캔버스 좌표계가 해상도에 따라 달라지므로, 런타임에 계산하는 것이 유일한 정답.

## 4. 현재 동작하는 플레이 흐름

코드 레벨에서 완성된 end-to-end 루프:

```
[채집·생산]
NpcScheduleController → Work 페이즈
    → ProducerNpcController: 작업 지점 이동 → 생산 대기 → dropOffPoint 납품
    → 계절 보정(SeasonModifier): 봄 농업 ×1.3, 겨울 전체 ×0.7

[가공]
플레이어: Workbench 앞 Space → CraftingUI 열림
    → 레시피 클릭 → CraftingService.TryCraft()
    → 재료 품질 가중평균 계산 → 결과물 ItemInstance(quality 1.2~1.5) 생성
    → Inventory.AddInstance() → 품질 메타 보존 인벤토리 적재

[판매]
플레이어: 핫바에서 ShopSlot 앞 Space → 진열
    → NpcScheduleController → Shopping 페이즈
    → NpcController: 상점 이동 → BrowsingShop
    → PurchaseEvaluator.Evaluate(profile, slot, rng)
    → 구매 성공: EconomyService.Deposit() → TierService 누적매출 갱신
    → 티어 임계 도달: TierService.OnTierAdvanced → Shop.ApplyTierSlots() → 진열 슬롯 확장

[저장/로드]
F5: SaveManager.SaveGameAsync() → LocalJsonSaveRepository
    → 인벤토리·핫바 ItemInstance (quality·price 포함) 직렬화 (version=3)
F9: LoadGameAsync() → ItemRegistry.Find(id, name) → ItemInstance 재생성
    → FriendshipService·HiringService 상태 복구
```

## 6. 기술 설계 측면에서 강조할 점

| 설계 원칙 | 적용 사례 | 효과 |
|---|---|---|
| 단일 책임 | EconomyService 재화 경로 단일화 | 멀티플레이 전환 시 한 곳만 수정 |
| 인터페이스 추상화 | ISaveRepository | Cloud Save 전환 시 SaveManager 무수정 |
