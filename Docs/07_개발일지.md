### Phase A — 데이터 레이어 재설계 (Step 1)

#### 배경 및 문제 인식
- `InventorySlot`이 `Item`(ScriptableObject 원형)을 직접 들고 있어 **품질·개별 가격·고유 ID** 저장 불가
- 기획서 Docs/02가 요구하는 "ItemData / ItemInstance 분리" 구조가 전혀 반영되지 않은 상태

#### 해결: `ItemInstance.cs` 신규 생성
```
Item (ScriptableObject) — 정적 원형 데이터 (변경 불가)
ItemInstance           — 런타임 동적 상태 (품질, 현재가격, 고유 ID)
```
- `instanceId`: `System.Guid.NewGuid()`로 스택 고유 식별
- `quality`: 1.0 기준 배수 (품질에 따라 NPC 평가 달라짐)
- `currentPrice`: 0이면 `data.basePrice` 폴백
- `EffectivePrice` 프로퍼티: 가격 계산 단일 경로

#### `InventorySlot.cs` 재작성
- 내부적으로 `ItemInstance`를 들고, **하위 호환 read accessor** 유지
  - `slot.item` → `instance?.data` (기존 읽기 코드 무수정)
  - `slot.count` → `instance.count` (기존 읽기 코드 무수정)
- **쓰기는 반드시 헬퍼 경유:** `Set()`, `SetInstance()`, `Clear()`, `AddCount()`
- 드래그 앤 드롭 스왑을 `SetInstance()` 참조 교환으로 구현 → 품질/가격 메타 유실 방지

**수정된 연관 파일:** `Inventory.cs`, `Hotbar.cs`, `InventorySlotUI.cs`, `StorageBox.cs`(List\<Item\> → List\<ItemInstance\>), `StorageUI.cs`

### Phase B — 서비스 레이어 도입 (Step 2)

#### 배경 및 문제 인식
- **재화 변경 경로가 3곳 이상:** `GameManager.money +=`, `GameManager.AddMoney()`, `직접 대입` 혼재
- 멀티플레이 전환 시 `NetworkVariable<int>` 한 곳만 수정하면 되도록 **단일 경로 강제** 필요
- `File.WriteAllText` 직접 호출 → UGS Cloud Save 전환 불가 구조
- `FindGameObjectsWithTag` 남용 → 퍼포먼스 및 동기화 리스크

#### `EconomyService.cs` 신규 생성
- **싱글톤, DefaultExecutionOrder -100** (씬 내 모든 시스템보다 먼저 초기화)
- `TrySpend(amount, reason)` / `Deposit(amount, reason)` — 모든 재화 변경 단일 입구
- `OnMoneyChanged` 이벤트 → UI 구독 방식
- `GameManager.cs`는 하위 호환 얇은 래퍼로 축소 (`GameManager.instance.money`는 읽기 전용 프록시)
- 미래: `_money`를 `NetworkVariable<int>`로 교체하면 멀티플레이 완성 (스타듀밸리 공유 지갑 방식)

#### `ISaveRepository.cs` + `LocalJsonSaveRepository.cs` 신규 생성
- 저장 백엔드를 인터페이스로 추상화
- `LoadAsync / SaveAsync / ExistsAsync` — 비동기 API
- `SaveManager.cs` 전면 재작성: `async Task SaveGameAsync()` / `LoadGameAsync()`
  - 기존 `GameManager.instance.money = 0` 직접 쓰기 → `EconomyService.ForceSet()` 교체
- 추후 `UGSCloudSaveRepository`로 교체 시 `SaveManager` 코드 무수정

#### `BuildingRegistry.cs` 신규 생성
- `FindGameObjectsWithTag("Building")` 안티패턴 제거
- 건물 GameObject가 생성/파괴 시 명시적 `Register() / Unregister()` 호출
- `BuildManager.cs` 개선: `EconomyService.TrySpend()` 실패 시 조기 반환, 성공 시만 건물 생성

**핵심 수정 포인트 (버그 예방):**
> 기존 코드는 잔액 확인 후 `AddMoney(-price)` 무조건 호출 → TryModifyMoney 실패 시 돈만 새는 레이스 컨디션 위험.  
> `TrySpend()` 단일 호출로 원자적 처리.

### Phase C — MBTI 경제 엔진 구현 (Step 3) ⭐

> 이 프로젝트의 핵심 차별점. NPC가 진열대 앞에 걸어가서, 물건을 구경하고, MBTI 성향에 따라 구매를 결정하는 루프.

#### `Item.cs` — ItemCategory 추가
```
Raw / Processed / Utility / Luxury / Tool
```
- NPC가 카테고리별로 다른 선호도를 보이게 하는 분류 기준
- `Tool` 카테고리는 진열 자체를 차단 (ShopSlot 진열 시 검증)

#### `NpcProfile.cs` — ScriptableObject 신규
MBTI 4축을 연속 실수(-1 ~ +1)로 표현:
| 필드 | 의미 |
|---|---|
| `traitEI` | -1(I 내향) ~ +1(E 외향): 외출/쇼핑 빈도 |
| `traitSN` | -1(S 감각) ~ +1(N 직관): 실용품 vs 사치품 선호 |
| `traitTF` | -1(T 사고) ~ +1(F 감정): 미래 구현 예정 |
| `traitJP` | -1(J 판단) ~ +1(P 인식): 미래 구현 예정 |
| `priceSensitivity` | 가격 민감도 (높을수록 비싸면 급감) |
| `utilityConsumption` | 실용품 소비 성향 배수 |
| `luxuryConsumption` | 사치품 소비 성향 배수 |

Inspector에서 에셋을 만들어 NPC에 드래그 드롭으로 성격 주입 가능.

#### `ShopSlot.cs` — 진열대 단위 신규
- 플레이어가 핫바에서 아이템을 꺼내 진열 (Tool/ToolType 차단)
- `displayPrice`: 플레이어가 직접 책정하는 가격
- `EffectiveDisplayPrice`: 미책정 시 `basePrice` 폴백
- NPC API `TryPurchaseByNpc()`: 구매 성공 시 `EconomyService.Deposit()` → 슬롯 비움
- `IInteractable` 구현: Space키로 진열/회수 토글

#### `Shop.cs` — 진열대 컨테이너 재작성
- 자식 `ShopSlot`들이 `Awake()`에서 자동 등록(`GetComponentInParent<Shop>`)
- `GetAvailableSlots()`: 비어 있지 않은 슬롯만 반환 → NPC가 조회
- 기존 "모두 판매" 디버그 기능 유지 (플레이어 직접 상호작용)

#### `PurchaseEvaluator.cs` — MBTI 구매 의사결정 순수 함수
```
구매 확률 계산 공식:
  1. idealPrice = basePrice × (1 + 0.5 × max(0, quality - 1))
  2. ratio = displayPrice / idealPrice
  3. baseProb:
       ratio ≤ 0.7  → 0.95 (할인가, 거의 무조건 구매)
       ratio = 1.0  → 0.70 (기본가)
       ratio ≥ 1.5  → 0.05 (고가, 거의 안 삼)
  4. categoryBonus (MBTI):
       Utility: S 성향(traitSN 음수)일수록 +보너스
       Luxury:  N 성향(traitSN 양수)일수록 +보너스
       Processed: N 소폭 선호
       Raw:       S 소폭 선호
  5. sensitivityPenalty = (ratio - 1) × 0.30 × priceSensitivity (ratio > 1일 때만)
  6. finalProb = clamp01(baseProb + categoryBonus - sensitivityPenalty)
  7. rng.NextDouble() < finalProb → 구매 결정
```
**설계 원칙:**
- 순수 함수 (외부 상태 의존 없음) → 유닛 테스트 친화적
- `UnityEngine.Random` 절대 사용 안 함 → 결정론 보장 (멀티플레이 서버 검증 가능)

#### `NpcController.cs` — FSM 확장 (Idle → MovingToShop → BrowsingShop)

**RNG 결정론화:**
- `UnityEngine.Random` → `System.Random` 인스턴스 (NPC별 독립 시드)
- 시드: `randomSeed` 명시 or `npcName + gameObject.name` 해시 → 같은 시드면 항상 같은 행동

**쇼핑 확률 공식:**
```
shoppingProb = 0.10 + 0.08 × traitEI + 0.04 × traitSN + 0.05 × (socialWeight - 0.5)
```
외향적(E)이고 사교적인 NPC일수록 더 자주 쇼핑하러 나온다.

**BrowsingShop 상태 신규:**
```
도착 → PickNextSlotToBrowse()
        → NavMesh로 슬롯 위치 이동
        → 슬롯 앞 도착 (slotArriveDistance)
        → browseDurationAtSlot 초 동안 "구경"
        → PurchaseEvaluator.Evaluate() 호출
        → BUY → TryPurchaseByNpc() → EconomyService.Deposit() → 종료
        → PASS → 다음 슬롯으로 (최대 maxSlotsPerVisit개)
```

## 세션 9 — 2026-04-11 · **워크샵 가공 시스템 (Process 3.0 빈 파이프 닫음)** ⭐

> Docs/02 4단계 자원 흐름 중 유일하게 비어 있던 **Process 3.0 "2차 가공 및 제작"** 단계를 채웠다. 이로써 ProducerNpc 가 만든 Raw 가 워크샵에서 quality 가 부여된 Processed 로 변환되고, ShopSlot 진열 → MBTI 평가 → Deposit 까지의 역-공급망 루프가 처음으로 끝까지 동작한다.

### 배경 및 문제 인식

세션 8 에서 ItemInstance.quality / EconomyService / ShopSlot / PurchaseEvaluator / TierService / ProducerNpcController 가 모두 자리를 잡았지만, **quality 를 만들어 주는 곳이 단 한 군데도 없었다.** 결과적으로:

- `PurchaseEvaluator.cs:52-53` 의 `idealPrice = basePrice × (1 + 0.5 × max(0, quality - 1))` 수식이 항상 quality=1 을 받음 → 부가가치 메커니즘 0% 가동
- `CraftingUI.cs` 가 `Inventory.AddItem(Item, int)` 만 호출 → 결과물 메타가 폴백값으로 박힘
- `RecipeData.cs` 는 단일 재료 4필드뿐 → 다중 재료/품질/티어/워크샵 종류 모두 결핍
- Workbench GameObject 가 존재하지 않아 "월드의 작업대" 라는 인터랙션 자체가 없음

### 변경 요약

#### `RecipeData.cs` — 확장 + 자동 마이그레이션
- `RecipeIngredient` 직렬화 클래스 신설 → 다중 재료 지원 (`List<RecipeIngredient>`)
- `WorkbenchType` enum 추가: `None / BasicWorkbench / Kitchen / Forge / SewingTable`
- 새 필드: `baseOutputQuality` (Range 0.5~3, 기본 1.2), `ingredientQualityWeight` (재료 품질 → 결과 반영 계수, 기본 0.3), `requiredTier`, `requiredWorkbench`
- 레거시 `inputItem`/`inputCount` 는 `[HideInInspector]` 로 숨기고 `OnValidate` 에서 단발성 마이그레이션 → 기존 에셋 손실 없이 새 구조로 자동 이전

#### `Inventory.cs` — `AddInstance(ItemInstance)` 신규
- 기존 `AddItem(Item, int)` 와 별도 경로 — quality / currentPrice 메타 보존이 의미 있을 때 사용
- `ItemInstance.CanStackWith()` 로 메타 일치 스택과만 합치고, 그 외엔 빈 슬롯에 통째로 `SetInstance` (참조 그대로 → 메타 손실 0)
- 기존 `AddItem` 호출자(채집/픽업)는 무영향

#### `CraftingService.cs` — 신규 (순수 헬퍼)
- `static TryCraft(RecipeData, Workbench)` 한 함수가 모든 검사·차감·생성 흐름을 담당
- 검사 순서: 워크샵 종류 → Tier → 재료 보유량 (실패 시 차감 없음)
- 결과 quality = `baseOutputQuality + ingredientQualityWeight × (avgIngredient - 1)` 로 계산 (MVP: avgIngredient=1.0 고정)
- 최종 `ItemInstance` 를 만들어 `Inventory.AddInstance` 로 푸시
- UI/입력에 무관한 순수 함수 → 추후 자동 가공 NPC, 디버그 콘솔, 단위 테스트가 동일 경로 재사용 가능

#### `Workbench.cs` — 신규 (월드 인터랙션 진입점)
- `IInteractable` 구현, `[RequireComponent(Collider)]`
- `Interact()` → `CraftingUI.instance.OpenForWorkbench(this)` 단순 위임
- `workbenchType` 필드로 종류 분기

#### `CraftingUI.cs` — 리팩토링
- 글로벌 토글 단일 모드 → **Workbench 컨텍스트 인식** 으로 전환
- `OpenForWorkbench(Workbench)`: 해당 종류 + 디버그용 None 레시피만 표시
- `ToggleUI()` (C 키): 디버그 글로벌 모드 — `_activeWorkbench=null` 로 호출하여 None 레시피만 보이게 유지
- 잠긴(티어/워크샵 부적합) 레시피는 `lockedColor` 로 회색 처리, 라벨에 🔒 (Tier N) 마크
- 클릭 시 모든 비즈니스 로직은 `CraftingService.TryCraft` 로 위임 — UI 는 표시·필터링만

### 검증 시나리오

플레이 모드에서 다음 흐름이 한 번에 동작해야 한다:

```
원목 ×2 보유
  ↓ Workbench(BasicWorkbench) 앞에서 Space
CraftingUI 열림 — "원목 가공" 레시피만 표시
  ↓ 클릭
✅ 가공 완료: 가공목재 ×1 (품질 1.40)
  ↓ ShopSlot 에 진열
NPC BrowsingShop → PurchaseEvaluator
  → idealPrice = basePrice × (1 + 0.5 × 0.4) = basePrice × 1.2
  → ratio 가 평소보다 낮음 → buy 확률 ↑
EconomyService.Deposit → 누적매출 ↑ → TierService 자동 평가
```

네거티브 케이스: requiredTier 미달 / 워크샵 종류 불일치 / 재료 부족 / 가방 풀 — 모두 콘솔 경고로 안내.

## 세션 10 — 2026-04-11 · **NPC 일과 스케줄 시스템 (Docs/03 J/P 축 완성)** ⭐

> GameClock 기반 24시간 사이클 위에 NpcDailySchedule + NpcScheduleController 를 올려
> "기상 → 작업 → 점심 → 쇼핑 → 귀가 → 수면" 흐름을 NPC 에 부여했다.
> J/P 축(traitJP)이 처음으로 실제 AI 연산에 반영된다.

### 배경 및 문제 인식

세션 8~9 까지 NpcController(소비형) 와 ProducerNpcController(생산형) 가 각자 독립 FSM 으로 동작했지만, **둘을 언제 키고 끄는지를 제어하는 상위 레이어가 없었다.** NPC 는 24시간 내내 쇼핑을 시도하거나 24시간 내내 생산만 했다. Docs/03 §1.2 "기상/출근/쇼핑/귀가" 일과 흐름이 전혀 반영되지 않았다. 또한 `traitJP` (J=계획/P=돌발) 가 NpcProfile 에 존재하지만 실제로 아무 연산에도 사용되지 않는 상태였다.

### 변경 요약

#### `Assets/Scripts/Services/GameClock.cs` — 신규
- `DefaultExecutionOrder(-80)` 싱글톤: EconomyService(-100) → TierService(-90) → **GameClock(-80)** → 나머지
- `secondsPerGameHour` 배속 조정 (10=테스트, 60=기본, 120=느린 진행)
- `CurrentHour(float)` / `CurrentDay(int)` 프로퍼티
- `OnHourTick(int)` — 정수 시각이 바뀔 때 1회 발화 → NpcScheduleController 구독
- `OnNewDay(int)` — 자정 통과 시 발화
- `ForceSet(hour, day, reason)` — 저장/로드 전용 복구 경로
- `GetTimeString()` — "HH:MM" 문자열 (UI 표시용)

#### `Assets/Scripts/NpcDailySchedule.cs` — 신규 ScriptableObject
- `SchedulePhase` enum: Sleep / WakeUp / Work / Lunch / Afternoon / Shopping / Evening / Rest
- `ScheduleWindow` 직렬화 클래스: `phase / startHour / endHour`
- `GetPhaseAt(float)`: currentHour 에 해당하는 페이즈 반환, 비어있는 시간대는 defaultPhase 폴백
- ContextMenu 3종 내장:
  - "기본 농부 스케줄 적용 (생산형 NPC)" — 7~12 Work + 15~17 Shopping
  - "기본 전문직 스케줄 적용 (오후형)" — 9~18 Work + 18~20 Shopping
  - "기본 주민 스케줄 적용 (소비형 NPC)" — 13~16 Shopping 위주

#### `Assets/Scripts/NpcScheduleController.cs` — 신규 MonoBehaviour
- `GameClock.OnHourTick` / `OnNewDay` 구독 → `EvaluateAndApply()` 정각 호출
- J/P drift 계산: `driftChance = max(0, traitJP) × 0.30`
  - P형(+1): 30% 확률로 스케줄 이탈 → Shopping(60%) 또는 Afternoon(40%) 으로 전환
  - J형(-1): 이탈 0%, 스케줄 엄격 준수
- `ApplyPhase()`: 페이즈별 서브 컨트롤러 Pause/Resume 조합
  - Sleep/Rest → 전체 정지
  - WakeUp/Afternoon/Evening → consumerController Resume (쇼핑 우선도 false)
  - Work → producerController Resume
  - Shopping → consumerController SetShoppingPriority(true) + Resume + TryForceShop()
- `ForceReevaluate()` 공개 API: 외부 이벤트(감사, 특수 행사)로 즉시 페이즈 갱신 가능

#### `Assets/Scripts/NpcController.cs` — 수정
- `_schedulePaused` 플래그: true 이면 `Update()` 전체 차단
- `_shoppingPriorityMode` 플래그: true 이면 쇼핑 확률 0.85~0.98 으로 상승 (기존 0.01~0.60)
- `Pause()`: 경로 취소 + 쇼핑 세션 정리 + Idle 전환
- `Resume()`: _schedulePaused 해제, idleTimer 리셋
- `SetShoppingPriority(bool)`: 쇼핑 우선 모드 전환
- `TryForceShop()`: Idle 상태이면 즉시 `BeginShoppingVisit()` 호출 (쇼핑 페이즈 즉각 반응)
- Inspector 디버그 필드: `debugSchedulePaused` / `debugShoppingPriority`

#### `Assets/Scripts/ProducerNpcController.cs` — 수정
- `_schedulePaused` 플래그: true 이면 `Update()` 차단
- `Pause()`: 경로 취소 → Idle 전환 (NPC 인벤토리는 보관 유지 — 재개 시 납품 시도)
- `Resume()`: _schedulePaused 해제, _idleTimer 리셋
- Inspector 디버그 필드: `_debugSchedulePaused`

#### `Assets/Scripts/SaveData.cs` / `SaveManager.cs` — 수정

- SaveManager: 로드 시 `GameClock.Instance.ForceSet()` 복구

## 기술 부채 & 알려진 리스크

| 항목 | 위험도 | 메모 |
|---|---|---|
| UI 미구현 | 높음 | 에셋 레퍼런스 확보 후 진행 예정 |
| UGS Cloud Save 미전환 | 중간 | `ISaveRepository` 인터페이스는 준비됨, 구현체만 교체 필요 |
| 멀티플레이 미구현 | 중간 | `EconomyService._money`를 `NetworkVariable<int>`로 교체 예정 |
| Farmland 실시간 타이머 | 낮음 | Update 기반 → 추후 이벤트 기반으로 최적화 |
| UI 찾기 `FindAnyObjectByType` | 낮음 | 나중에 직접 참조 또는 이벤트 구독으로 교체 권장 |
