## 2026-06-24~2026-06-25 - Unity Editor crash 원인 분리 및 D3D11 수리

### 문제

- Unity Editor가 Console compile error가 아니라 Bug Reporter와 함께 강제 종료됨.
- 일반 C# 오류가 아니라 native graphics-device crash 가능성이 높았음.

### 조사

- `Editor.log`와 crash artifact를 확인.
- 핵심 로그:
  - `d3d12: swapchain present failed (887a0005)`
  - `d3d12: Device failed error (887a0005)`
  - `d3d12: Device removed reason (887a0006)`
  - `Unrecoverable D3D12 device error`

### 수리

- Standalone graphics API를 자동/D3D12 대신 Direct3D 11 고정으로 변경.
- 상세 보고서:
  - `PROJECT_PA_CRASH_REPORT_20260624.md`
  - `PROJECT_PA_CRASH_REPORT_20260625.md`

### 검증

- `-force-d3d11` load 통과.
- Project graphics API load 통과.
- D3D11 상태에서 Final Route regression 통과.

### 남은 일

- D3D12로 되돌리지 않기.
- crash report는 자동화 루프에서 launch-heavy 작업 전 사람이 baseline으로 인정해야 함.

- 시연 씬에서 플레이어는 보이지만 핫바/인벤토리 슬롯의 아이템이 비어 보였다.
- 스타터 아이템이 실제 플레이어가 아닌 다른 `Inventory/Hotbar`에 들어갈 수 있었다.
- 일부 NPC가 기본 캡슐 또는 모델 미적용 상태로 남아 프로토타입 시연성이 떨어졌다.

### 수정
- `HotbarUI`, `InventoryUI`
  - 런타임에 `Player` 태그 오브젝트의 `Inventory/Hotbar`를 우선 참조하도록 보강.
  - 기존 UI 참조가 비어 있어도 슬롯 UI를 다시 묶고 새로고침하도록 처리.
- `InventorySlotUI`
  - 아이콘이 없는 아이템도 베이지 슬롯과 짧은 텍스트 라벨로 표시되도록 fallback 표시 추가.
  - 슬롯/툴팁/드래그 레이어 null 예외 방어.
- `Inventory`
  - 중복 `Inventory`가 있을 때 `Player` 태그가 붙은 인벤토리를 싱글톤 우선 대상으로 유지.
- `PA_PlayableDayBuilder`
  - 스타터 아이템을 `FindFirstObjectByType` 결과가 아니라 실제 `Player`의 `Hotbar`에 주입.
  - NPC별로 `C-02`~`C-09` 모델을 순차/역할 기반으로 자동 배정.
  - 기존 `NpcModel_` 자식이 중복될 경우 새 모델만 남기도록 정리.

### 검증
```text

결과: 성공, 오류 0개, 경고 CS8785 1개

dotnet build Assembly-CSharp-Editor.csproj --no-restore
결과: 성공, 오류 0개, 경고 CS8785/CS0414
```

### Phase A — 데이터 레이어 재설계 (Step 1)

#### 배경 및 문제 인식
- `InventorySlot`이 `Item`(ScriptableObject 원형)을 직접 들고 있어 **품질·개별 가격·고유 ID** 저장 불가
- 기획서 Docs/02가 요구하는 "ItemData / ItemInstance 분리" 구조가 전혀 반영되지 않은 상태

#### 해결: `ItemInstance.cs` 신규 생성
```
Item (ScriptableObject) — 정적 원형 데이터 (변경 불가)
ItemInstance           — 런타임 동적 상태 (품질, 현재가격, 고유 ID)
```
- `instanceId`: `System.Guid.NewGuid()`로 스택 고유 식별
- `quality`: 1.0 기준 배수 (품질에 따라 NPC 평가 달라짐)
- `currentPrice`: 0이면 `data.basePrice` 폴백
- `EffectivePrice` 프로퍼티: 가격 계산 단일 경로

#### `InventorySlot.cs` 재작성
- 내부적으로 `ItemInstance`를 들고, **하위 호환 read accessor** 유지
  - `slot.item` → `instance?.data` (기존 읽기 코드 무수정)
  - `slot.count` → `instance.count` (기존 읽기 코드 무수정)
- **쓰기는 반드시 헬퍼 경유:** `Set()`, `SetInstance()`, `Clear()`, `AddCount()`
- 드래그 앤 드롭 스왑을 `SetInstance()` 참조 교환으로 구현 → 품질/가격 메타 유실 방지

**수정된 연관 파일:** `Inventory.cs`, `Hotbar.cs`, `InventorySlotUI.cs`, `StorageBox.cs`(List\<Item\> → List\<ItemInstance\>), `StorageUI.cs`

### Phase B — 서비스 레이어 도입 (Step 2)

#### 배경 및 문제 인식
- **재화 변경 경로가 3곳 이상:** `GameManager.money +=`, `GameManager.AddMoney()`, `직접 대입` 혼재
- 멀티플레이 전환 시 `NetworkVariable<int>` 한 곳만 수정하면 되도록 **단일 경로 강제** 필요
- `File.WriteAllText` 직접 호출 → UGS Cloud Save 전환 불가 구조
- `FindGameObjectsWithTag` 남용 → 퍼포먼스 및 동기화 리스크

#### `EconomyService.cs` 신규 생성
- **싱글톤, DefaultExecutionOrder -100** (씬 내 모든 시스템보다 먼저 초기화)
- `TrySpend(amount, reason)` / `Deposit(amount, reason)` — 모든 재화 변경 단일 입구
- `OnMoneyChanged` 이벤트 → UI 구독 방식
- `GameManager.cs`는 하위 호환 얇은 래퍼로 축소 (`GameManager.instance.money`는 읽기 전용 프록시)
- 미래: `_money`를 `NetworkVariable<int>`로 교체하면 멀티플레이 완성 (스타듀밸리 공유 지갑 방식)

#### `ISaveRepository.cs` + `LocalJsonSaveRepository.cs` 신규 생성
- 저장 백엔드를 인터페이스로 추상화
- `LoadAsync / SaveAsync / ExistsAsync` — 비동기 API
- `SaveManager.cs` 전면 재작성: `async Task SaveGameAsync()` / `LoadGameAsync()`
  - 기존 `GameManager.instance.money = 0` 직접 쓰기 → `EconomyService.ForceSet()` 교체
- 추후 `UGSCloudSaveRepository`로 교체 시 `SaveManager` 코드 무수정

#### `BuildingRegistry.cs` 신규 생성
- `FindGameObjectsWithTag("Building")` 안티패턴 제거
- 건물 GameObject가 생성/파괴 시 명시적 `Register() / Unregister()` 호출
- `BuildManager.cs` 개선: `EconomyService.TrySpend()` 실패 시 조기 반환, 성공 시만 건물 생성

**핵심 수정 포인트 (버그 예방):**
> 기존 코드는 잔액 확인 후 `AddMoney(-price)` 무조건 호출 → TryModifyMoney 실패 시 돈만 새는 레이스 컨디션 위험.

### Phase C — MBTI 경제 엔진 구현 (Step 3) ⭐

> 이 프로젝트의 핵심 차별점. NPC가 진열대 앞에 걸어가서, 물건을 구경하고, MBTI 성향에 따라 구매를 결정하는 루프.

#### `Item.cs` — ItemCategory 추가
```
Raw / Processed / Utility / Luxury / Tool
```
- NPC가 카테고리별로 다른 선호도를 보이게 하는 분류 기준
- `Tool` 카테고리는 진열 자체를 차단 (ShopSlot 진열 시 검증)

#### `NpcProfile.cs` — ScriptableObject 신규
MBTI 4축을 연속 실수(-1 ~ +1)로 표현:
| 필드 | 의미 |
|---|---|
| `traitEI` | -1(I 내향) ~ +1(E 외향): 외출/쇼핑 빈도 |
| `traitSN` | -1(S 감각) ~ +1(N 직관): 실용품 vs 사치품 선호 |
| `traitTF` | -1(T 사고) ~ +1(F 감정): 미래 구현 예정 |
| `traitJP` | -1(J 판단) ~ +1(P 인식): 미래 구현 예정 |
| `priceSensitivity` | 가격 민감도 (높을수록 비싸면 급감) |
| `utilityConsumption` | 실용품 소비 성향 배수 |
| `luxuryConsumption` | 사치품 소비 성향 배수 |

Inspector에서 에셋을 만들어 NPC에 드래그 드롭으로 성격 주입 가능.

#### `ShopSlot.cs` — 진열대 단위 신규
- 플레이어가 핫바에서 아이템을 꺼내 진열 (Tool/ToolType 차단)
- `displayPrice`: 플레이어가 직접 책정하는 가격
- `EffectiveDisplayPrice`: 미책정 시 `basePrice` 폴백
- NPC API `TryPurchaseByNpc()`: 구매 성공 시 `EconomyService.Deposit()` → 슬롯 비움
- `IInteractable` 구현: Space키로 진열/회수 토글

#### `Shop.cs` — 진열대 컨테이너 재작성
- 자식 `ShopSlot`들이 `Awake()`에서 자동 등록(`GetComponentInParent<Shop>`)
- `GetAvailableSlots()`: 비어 있지 않은 슬롯만 반환 → NPC가 조회
- 기존 "모두 판매" 디버그 기능 유지 (플레이어 직접 상호작용)

#### `PurchaseEvaluator.cs` — MBTI 구매 의사결정 순수 함수
```
구매 확률 계산 공식:
  1. idealPrice = basePrice × (1 + 0.5 × max(0, quality - 1))
  2. ratio = displayPrice / idealPrice
  3. baseProb:
       ratio ≤ 0.7  → 0.95 (할인가, 거의 무조건 구매)
       ratio = 1.0  → 0.70 (기본가)
       ratio ≥ 1.5  → 0.05 (고가, 거의 안 삼)
  4. categoryBonus (MBTI):
       Utility: S 성향(traitSN 음수)일수록 +보너스
       Luxury:  N 성향(traitSN 양수)일수록 +보너스
       Processed: N 소폭 선호
       Raw:       S 소폭 선호
  5. sensitivityPenalty = (ratio - 1) × 0.30 × priceSensitivity (ratio > 1일 때만)
  6. finalProb = clamp01(baseProb + categoryBonus - sensitivityPenalty)
  7. rng.NextDouble() < finalProb → 구매 결정
```
**설계 원칙:**
- 순수 함수 (외부 상태 의존 없음) → 유닛 테스트 친화적
- `UnityEngine.Random` 절대 사용 안 함 → 결정론 보장 (멀티플레이 서버 검증 가능)

#### `NpcController.cs` — FSM 확장 (Idle → MovingToShop → BrowsingShop)

**RNG 결정론화:**
- `UnityEngine.Random` → `System.Random` 인스턴스 (NPC별 독립 시드)
- 시드: `randomSeed` 명시 or `npcName + gameObject.name` 해시 → 같은 시드면 항상 같은 행동

**쇼핑 확률 공식:**
```
shoppingProb = 0.10 + 0.08 × traitEI + 0.04 × traitSN + 0.05 × (socialWeight - 0.5)
```
외향적(E)이고 사교적인 NPC일수록 더 자주 쇼핑하러 나온다.

**BrowsingShop 상태 신규:**
```
도착 → PickNextSlotToBrowse()
        → NavMesh로 슬롯 위치 이동
        → 슬롯 앞 도착 (slotArriveDistance)
        → browseDurationAtSlot 초 동안 "구경"
        → PurchaseEvaluator.Evaluate() 호출
        → BUY → TryPurchaseByNpc() → EconomyService.Deposit() → 종료
        → PASS → 다음 슬롯으로 (최대 maxSlotsPerVisit개)
```

## 세션 12 — 2026-04-12 · **상점 단계별 진화 (Docs/05 §3)**

> TierService 의 `OnTierAdvanced` 이벤트를 Shop 이 구독해,
> 티어가 오를 때마다 상점 슬롯 수가 자동으로 늘어난다.
> 기획서의 "가판대 → 잡화점 → 마트 → 백화점" 4단계 진화의 코드 뼈대가 완성됐다.

### 배경 및 문제 인식

세션 8~11 까지 TierService 가 승급 이벤트를 발화하고 있었지만
**상점은 아무 반응도 하지 않았다.** 슬롯 수는 씬 배치 시 고정이었고,
Tier 2 로 승급해도 Shop 슬롯이 4개에서 늘어나지 않아 기획서의 확장감이 0 이었다.

### 변경 요약

#### `TierDefinition.cs` — 상점 슬롯 필드 추가
- `shopSlotCount (int)`: 이 티어에서 활성화할 슬롯 수. **0 이면 이전 티어 값 캐스케이드.**
  - 권장값: Tier0=4(가판대), Tier2=8(잡화점), Tier3=12(마트), Tier4=20(백화점)
  - Tier1=0 으로 두면 Tier0 의 4슬롯 유지 (설정 부담 없음)
- `shopStageName (string)`: UI/로그에 표시할 단계 이름 (가판대 / 잡화점 / 마트 / 백화점)

#### `TierService.cs` — 공개 API 2개 추가
- `GetDefinition(int tier)` — 기존 `private` 메서드를 `public` 으로 승격 (Shop, 추후 UI 에서도 활용)
- `GetEffectiveShopSlotCount(int tier)` — tier 0 부터 순회해 마지막으로 설정된 `shopSlotCount` 반환 (캐스케이드 처리)

#### `Shop.cs` — 티어 반응형 슬롯 관리 추가
- `public List<ShopSlot> managedSlots` — Inspector 에서 씬의 ShopSlot 오브젝트를 **활성화 순서대로** 등록
- `Start` → `TierService.OnTierAdvanced` 구독 + `ApplyTierSlots()` 즉시 호출 (로드 직후도 반영)
- `ApplyTierSlots()`: `GetEffectiveShopSlotCount(currentTier)` 개수만큼 `managedSlots[i].SetActive(true)`, 나머지 `false`
- `GetAvailableSlots()` — `activeSelf` 필터 추가: 비활성 슬롯은 NPC 쇼핑 목록에서 자동 제외
- `ResolveStageName(tier)` — 현재 tier 이하 중 최근 `shopStageName` 을 찾아 로그에 출력

### 씬 설정 방법 (씬 구성 시)

1. Shop 자식으로 ShopSlot GameObject 를 **최대 슬롯 수(20개)만큼** 배치, 모두 Active 시작
2. `Shop.managedSlots` 에 SlotA~SlotT 를 활성화 순서대로 드래그
3. 각 `TierDefinition` 에셋에서 `shopSlotCount` 와 `shopStageName` 설정
4. 플레이 모드에서 TierService 가 승급 이벤트를 발화하면 슬롯이 자동으로 켜지는지 확인

### 검증 시나리오

```
Tier0 시작 → 🏪 상점 진화: [가판대] 슬롯 4개 활성화
TierService 강제 승급 (Tier2) → 🏪 상점 진화: [잡화점] 슬롯 8개 활성화
NPC 쇼핑: managedSlots[4..7] 의 진열품도 정상 구매
```

| 파라미터 | 황금값 | 근거 |
|---------|--------|------|
| `acceleration` | 18 m/s² | 0→5 m/s 약 0.28s — 가볍되 무게감 |

- **CharacterController 텔레포트 주의:** `transform.position` 직접 대입 시 내부 누적 이동량이 한 프레임 뒤 덮어쓴다. 반드시 `cc.enabled = false` → 위치 설정 → `cc.enabled = true` 순서.
- **카메라 Lerp 스킵 필수:** `CameraController.smoothSpeed = 5f` 는 장거리 워프(Y+100)를 몇 초간 긴 패닝으로 보여준다. `SnapToTarget()` 으로 텔레포트 프레임에 offset 위치 즉시 반영.
- **페이드 루틴:** `Time.unscaledDeltaTime` 사용 → 추후 TimeScale 정지 UI(스마트폰 오버레이 등) 와 충돌하지 않음.

### 다음 단계

1. 씬에 `[Services] > ScreenFader` GameObject 배치 (컴포넌트만 추가하면 Canvas 자동 생성)
2. 기존 `B-01 가판대 (Market Stall)` 외부에 `Door_Out`, 실내 영역에 `Door_In` 배치해서 **파일럿 테스트**
3. 테스트 통과 후 — 문라이터2식 가격 탐색 루프(세션 16 예정) 착수: `ShopSlot.playerSetPrice` + `PurchaseEvaluator` 반응 4단계 분기.

### 메모

어떤 방식으로 실내를 구현할지 처음엔 Additive Scene 에 끌렸는데, 한 번 더 생각해보니 **NavMesh 분리 문제 + Services 싱글톤 참조 이슈**가 MVP 기간에 감당할 리스크가 아니었다. Y=+100 오프셋은 투박해 보이지만 Stardew·Moonlighter 도 같은 방식이다. 졸작은 "동작하는 게 우선, 예쁜 구조는 그다음". `BuildingEntrance` 를 양방향 하나의 컴포넌트로 만든 건 의도적 — 실내 문과 실외 문이 사실상 대칭이라 별도 클래스 분리가 오버엔지니어링이다.

### 수정 파일

| 파일 | 수정 내용 |
|---|---|
| `UI/SmartphoneUI.cs` | `activePos` 하드코딩 제거 → `ComputeActivePos()` 메서드, `_canvas` 참조 캐싱 |
| `PlayerController.cs` | `SmartphoneUI.instance.IsOpen` 체크 추가 (InventoryUI 와 동일 패턴) |
| `UI/InventoryAnchorFollower.cs` | `FindHeadBone()` 추가, `headBoneOffset` / `worldOffset` 필드 분리, `OnEnable` / `Awake` 에서 재탐색 |

### ⚠️ Unity 에디터에서 할 작업

1. **Player 태그 확인**: Player GO 선택 → Inspector 상단 Tag 드롭다운 → `Player` 로 설정
2. **Player Animator 확인**: Rig 탭 → Animation Type = `Humanoid`, Avatar 연결됐는지 확인
   - Humanoid 설정이 되어있으면 `Animator.GetBoneTransform(Head)` 로 자동 탐색 성공
3. **빌드 후 InventoryPanel Inspector 확인**: `Head Bone` 필드에 자동으로 뼈가 잡히는지 Play 모드에서 확인
   - 비어있으면 `worldOffset (0, 1.8, 0)` 폴백으로 동작

### 메모

Free Aspect 해상도 문제는 `CanvasScaler` 가 `ScaleWithScreenSize` + `matchWidthOrHeight=0.5` 이면 캔버스 rect 가 실제 해상도에 따라 달라지기 때문에 발생. `anchoredPosition` 의 절댓값은 캔버스 좌표계 기준이므로 캔버스 크기가 바뀌면 같은 값이라도 다른 위치가 된다. "중앙" 같은 상대적 위치는 항상 런타임 계산으로 처리해야 한다. 인벤토리 추적은 Mixamo Humanoid Avatar 가 설정된 경우 `HumanBodyBones.Head` 로 완벽하게 작동. 설정 안 된 경우 이름 기반 폴백으로 커버.

## 2026-05-08 - NPC 관절 꺾임 안전 모드 보정

## 2026-05-12 - 빌딩 스케일 정규화 기준 추가

### 문제

- 플레이어/NPC가 2배 스케일 기준으로 커져 있는데, Tripo3D에서 가져온 빌딩 FBX는 원본 bounds가 제각각이라 캐릭터와 월드 크기가 맞지 않았다.
- 프리팹 scale을 수동으로 만지면 나중에 모델을 교체할 때 다시 틀어질 수 있었다.

### 조치

- `PA_ContentAutoIntegrator`에 캐릭터 기준 높이 `3.6m`를 명시하고 B01~B12의 목표 월드 크기를 재정의했다.
- 모델 생성 시 Renderer bounds를 읽어 목표 크기에 맞게 uniform scale로 자동 보정한다.
- 보정 후 모델 중심을 XZ 원점에 맞추고 바닥을 Y=0에 붙여, Collider/NavMeshObstacle/상호작용 위치가 일관되도록 했다.
- 검증 단계에서 프리팹의 대표 `BoxCollider.size`가 목표 크기와 다르면 경고하도록 보강했다.
