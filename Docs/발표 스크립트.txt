
Slide 1: 프로젝트 개요 및 정체성
[내용] 노동에서 경영으로, 너굴 상점의 주인이 된 플레이어.

[스크립트] "안녕하십니까. 저는 기존 심라이프의 반복적인 노동에서 벗어나 유저가 직접 상점을 운영하고 섬의 방향성을 결정하는 '역-공급망 경영 시뮬레이션', 프로젝트 파이오니어 어시스턴스를 졸업작품으로 할 신동준입니다. 
유저는 개척 지원 지점장으로서 NPC를 관리하고 섬을 성장시키는 '매니지먼트의 즐거움'을 경험하게 됩니다."

Slide 2: 벤치마킹 (Benchmarking)
[내용] 동물의 숲, 스타듀밸리, 딩컴, 데이브 더 다이버의 핵심 요소 차용.

[스크립트] "저는 네 가지 게임을 레퍼런스로 삼았습니다. '동물의 숲' 너굴 상점의 역할을 유저에게 부여했고, '스타듀밸리'의 깊이 있는 경제와 관계 시스템을 가져왔습니다. '딩컴'의 개척 시스템을 통해 섬의 개성을 살렸으며, 특히 '데이브 더 다이버'처럼 유쾌한 연출과 직원 고용 시스템을 통해 다음 해금 항목이 기대되는 상점 운영의 재미를 구현하고자 합니다

Slide 3: 핵심 게임 메커니즘 (Core Mechanism)
[내용] 자원 채취 위임 -> 유저 상점 매입 -> 가공 및 유통 -> 재투자 루프.
[스크립트] "게임의 핵심은 '역-공급망'입니다. NPC가 자원을 채취해오면 유저는 이를 매입하여 유동성을 공급합니다. 이후 공방에서 가공을 거쳐 부가가치를 높이고, 다시 NPC에게 판매하여 얻은 수익으로 마을 인프라를 확장합니다. 이는 유저가 지루한 반복 작업에서 벗어나 전략적 판단에 집중하게 만듭니다."

Slide 4: 시간 흐름 및 해금 시스템 (Tiers)
[내용] 게임 내 시간 설정 및 4단계 본사 승인 티어 표.
[스크립트] 성장은 '본사 승인 등급'에 따라 해금됩니다. 각 티어를 달성할 때마다 데이브 더 다이버와 같은 유쾌한 연출을 통해 상점 확장, 특수 도구, 무역항 등이 해금되며 플레이어에게 지속적인 동기를 부여합니다."

Slide 5: 멀티플레이 시스템 구축 (Multiplayer)
[내용] Client-Host 모델 및 Unity Relay 활용 이유.
[스크립트] "멀티플레이는 별도 서버 비용이 없는 Host-Client 방식을 선택했습니다. 호스트는 경제 로직과 NPC AI를 통제하는 서버 역할을 하며, 클라이언트는 파견 파트너로 참여합니다. Unity Relay 서비스를 통해 NAT 환경에서도 안정적인 연결을 보장하여 친구와 함께 섬을 개척할 수 있습니다."

Slide 6: 데이터 동기화 방식 (Sync Strategy)
[내용] NetworkVariable, 권한(Authority), RPC(Server/Client) 처리.
[스크립트] "데이터 일관성을 위해 매니저 객체와 컴포넌트를 구성했습니다. 상태 데이터는 NetworkVariable로 실시간 동기화하며, 보안을 위해 호스트 권한 모델을 사용합니다. 아이템 구매와 같은 일회성 이벤트는 ServerRPC로 요청하고, 결과는 ClientRPC로 모든 유저에게 반영하여 상호작용의 지속성과 보존성을 보장합니다."

Slide 7: 멀티플레이 시퀀스 다이어그램
[내용] 클라이언트-서버-Relay 간의 데이터 흐름 시각화.
[스크립트] 
Client 는상호작용을 시작하는 플레이어.UGS Relay는 데이터 전달을 중계하는 서버.
Host (Server)는 게임 로직을 검증하고 데이터를 소유하는 방장. Other Clients는 변경된 월드 상태를 전달받는 다른 유저들입니다

나무를 베는 상황을 시퀀스로 보면 클라이언트가 나무를 베고 싶어서 도끼로 나무를 상호작용하여 서버rpc를 호출합니다
해당 요청이 릴레이를 거쳐 호스트에게 도달하게 되면 호스트는 플레이어가 있는 좌표에 나무가 있는지 거리는 적당한지 등등을 검증합니다 그래서 검증이 통과한다면 상태 동기화를 담당하는 네트워크변수를 변경하고 이 변경된 정보를 호스트는 클라이언트 rpc 또는 네트워크변수 동기화를 통해 모든 클라이언트에게 해당 좌표의 나무가 쓰러지는 애니메이션 재생을 명령하는 것으로 모든 유저의 화면에 결과를 반영합니다.

슬라이드 18:

메모리 효율을 위해 정적 데이터인 ScriptableObject와 실시간 상태 데이터인 Instance 클래스를 분리했습니다.

모든 아이템 인스턴스가 각각의 정보를 다 들고 있으면 메모리가 낭비됩니다. 따라서 변하지 않는 정보(이름, 기본가, MBTI 가중치)는 ScriptableObject에 단 하나만 저장하고, 실제 월드에 존재하는 아이템들은 이 원본을 '참조'만 함으로써 수천 개의 아이템이 존재해도 메모리 부하를 최소화했습니다.

유저가 자유롭게 가격을 책정할 수 있지만, 실제 판매 성공 여부는 방문하는 NPC의 성향 파라미터와 아이템의 속성이 물리적으로 연산되어 결정됩니다.

슬라이드 19:

보시는 바와 같이 모든 소유주는 독립적인 Inventory를 가지며, 그 안에서 ItemInstance가 유기적으로 이동합니다. 특히 상점의 진열대인 ShopSlot 엔티티를 별도로 분리 설계함으로써, 유저 주도의 자유로운 가격 책정과 NPC의 MBTI 로직이 데이터 레벨에서 실시간으로 상호작용할 수 있도록 구현할 것 입니다 .

시스템이 정한 기준가(IdealPrice)가 아닌, 유저가 실시간으로 입력하는 가격은 ShopSlot 엔티티의 DisplayPrice 필드에 저장됩니다 . NPC AI는 이 필드 값과 자신의 MBTI 성향 파라미터를 대조하여 구매 여부를 연산하는 **'전략적 가격 탐색 로직'**의 기반이 됩니다 .

마지막 슬라이드

마지막으로 멀티플레이 환경에서의 데이터 지속성 설계입니다.

교수님꼐서 Host-Client 모델의 한계로 클라이언트들은 호스트 없이는 플레이를 못한다는 점을 집어 주셨는데 대안으로 클라우드 스냅샷 방식을 찾아왔습니다.

호스트는 게임 종료 시 최신 JSON 세이브 데이터를 클라우드 저장소에 업로드하여 세션의 마지막 상태를 보존합니다.
만약 호스트가 부재중일 때 클라이언트가 접속을 시도하거나 플레이를 이어가길 원한다면, 클라우드에서 스냅샷 데이터를 내려받아 지점장 대리로서 권한을 승계받습니다. 이를 통해 사용자는 호스트의 접속 여부와 관계없이 자신의 섬을 지속적으로 발전시킬 수 있습니다.

여기서의 데이터 흐름은
호스트에서 데이터를 직렬화 하여 게임의 상태를 텍스트로 클라우드에 동기화가 됩니다 이후 다른 클라이언트 중에서 새로운 호스트를 선출하여 인증하고 임시 호스트가 되어 데이터를 로드하게 되고 플레이를 이어나갈 수 있게 됩니다

해당 클라우드 서비스는 Unity Gaming Services를 기반으로 해서 별도 백엔드 구축 없이 유니티 계정과 연동하여 JSON 데이터를 저장하고 불러오는 SDK를 활용할 예정입니다.
