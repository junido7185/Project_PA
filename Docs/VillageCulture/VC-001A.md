# VC-001A - Next-Day Market Visual Change

Status: timing/state validated; Task 106 visual replacement implemented, live composition pending
Date: 2026-06-26

## Goal

Add one small next-day plaza or market visual change that reflects the previous day's sold product category, while preserving Project_PA's identity as a reverse supply-chain cozy management life-sim.

The feature is intentionally small: it proves that a product category sold through the shop can become visible in the village on the following day. It is not a new economy system, a save-system change, or a decorative clone of any reference project.

## Selected Category

Selected category: `Processed`

Reason:

- The current Day 1 default route sells `BreadLoaf`.
- `BreadLoaf` is an existing Project_PA item under the `Processed` category.
- `ShopSlot.TryPurchaseByNpc` already records sales through `SalesLogManager.RecordSale`.
- `VillageChangeSignalController` already reads recent sales and identifies `Processed` as a village direction category.

## Implementation

Added:

- `Assets/Scripts/VillageCultureVisualController.cs`
- `Assets/Editor/PA_VillageCultureVisualValidator.cs`

Runtime behavior:

- Creates a Project_PA-owned runtime sidecar named `PA_VillageCultureVisualController`.
- Creates a runtime visual root named `PA_VillageCulture_Processed`.
- The visual root is inactive at Day 1 start.
- A `Processed` sale creates a pending next-day change.
- The visual does not activate immediately after the sale.
- On the next `DayPreparation` phase, the visual appears as a warm processed-goods prep corner near the market hub.
- A short hint appears once and then hides itself.

No scene object from Project_D was used. The original 2026-06-26 blockout used Unity primitives; Task 106 replaces that blockout with existing Project P.A. assets as documented below.

## Task 092 — Raw Category Extension (2026-07-17)

The same sidecar now accepts `Raw` as a second implemented category without changing the
v10 save contract. `SalesLogManager.GetRecent` is newest-first, so if multiple tracked
sales arrive between refreshes, the most recent `Raw` or `Processed` sale becomes the
single next-day representative change.

Raw behavior:

- A real `Raw` sale creates a pending change on its sale day.
- The current-day world does not change immediately.
- On a later `DayPreparation`, only `PA_VillageCulture_Raw` becomes active.
- The existing pending/active category strings save and restore `Raw`; no new field was added.
- The Raw hint explains that producer storage and collection capacity has appeared.

Unlike the original VC-001A blockout, the new Raw root creates no primitive cube. It uses
the existing CC0 Quaternius Nature Pack `Prop_WoodLog` and `Prop_Rock` Resource prefabs,
plus the Project P.A.-owned `B10_Cottage_ShopSign` mesh with a Korean
`원자재 수거처` label. Runtime copies have Collider and functional MonoBehaviour
components removed, so the visual cannot create an invisible obstacle or pretend to be an
interactive storage box.

Runtime and Editor C# builds and static resource/state contracts pass. Actual GameCamera
before/after, sign facing, scale, overlap, and route readability remain unverified because
the common validator capture path has already caused the same native `Camera.Render()`
crash twice; a third Unity launch is prohibited until that path is approved and replaced.

## Task 108 — Luxury Craft Display Extension (2026-07-27)

The existing sale observer now accepts `Luxury` as the fourth implemented category. The
existing sellable `목제 가구` and `의류` items both use `ItemCategory.Luxury`; their real
recipes remain connected to the Basic Workbench and B08 Sewing Table respectively. A Luxury
sale creates a pending change, leaves the sale-day world unchanged, and activates only on a
later `DayPreparation`. The existing v10 pending/active category strings serialize `Luxury`
without a new field, version, migration, or restore owner.

The Luxury root loads `Building_B08_SewingTable` but instantiates only its `prefab/Visual`
child at a bounded 0.48 scale. The pastel wood, fabric rolls, and mannequin give the visual a
real lifestyle-craft silhouette; the existing Project P.A. sign labels it `공예 전시대`.
The wrapper that owns the Sewing Table `Workbench`, `BoxCollider`, and `NavMeshObstacle` is
never instantiated.

Every cloned Collider, Rigidbody, NavMeshObstacle, MonoBehaviour, and Light is disabled and
removed. Processed, Raw, Utility, and Luxury roots are mutually exclusive, so the display
cannot become a second crafting station, route blocker, product source, reward, or unlock.

Runtime and Editor builds complete with zero errors and 27/27 corrected static contracts
pass. The first audit run produced two selector false negatives: B08 stores its `Visual` name
as a prefab override, and save/package files were already dirty before Task 108. The corrected
audit checks the authored override and verifies that existing protected-file diffs contain no
Task 108 markers.

B08's function and placement are already connected, but its game-camera-facing visual
finalization and individual Tripo provenance remain open. A same-camera Luxury sale-day/
next-day/save-restore check must still judge scale, facing, sign readability, overlap, routes,
and whether the sewing-derived silhouette reads broadly enough as craft culture. Unity was
not launched under the repeated direct-render native-crash boundary.
