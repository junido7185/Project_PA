## 3. P10 보완 — 걷고 생활할 수 있는 섬

이번 시작 메시지의 아트 방향은 **따뜻한 로우폴리 해안 마을**, 가까운 활동이 자연스럽게 발견되는 동선, 읽히는 높이 변화, 기존 로컬 자산의 일관된 크기·색·재질이다. 완성 여부를 색 교체나 나무 개수로 판정하지 않는다.

- 항구/보급 → 채집/낚시/초원 → 정착/작업대 → 집/상점의 실제 보행 경로를 연결한다. 주요 활동 발견 간격 10~20초는 실제 탐험으로 확인하며 직선 거리/이동 속도 계산을 보행 검증으로 대신하지 않는다. Canon의 전체 데모 시간 목표도 실제 완주 시간과 함께 보고한다.
- 단차는 절벽 면·윗선·재질과 **실제로 걸을 수 있는 경사로/통로**로 읽히게 한다. 길이 도랑처럼 보이거나 광장이 넓은 색 평면으로 남으면 지면 표현/가장자리/드레싱을 직접 고친다. 자원·건물·NPC를 가리는 장식은 줄인다.
- 기존 `WorldGeneratedIslandDebugView`, `WorldChunkTerrain`, `WorldIslandGenerator`, `WorldNavigationService`, 데모 배치/presentation을 재사용·한정 확장할 수 있다. 메시·콜라이더·기존 서비스의 NavMeshLink/재빌드 연결과 직접 필요한 로컬 prefab/material/scene binding을 함께 수정할 수 있다. 모든 World 작업을 새 테스트 씬으로 옮겨 Demo256 개선을 피해 가지 않는다.
- 이 허용은 새 WorldGrid/지형/Placement/Save 권위, 전체 생성기 재작성, 섬 전체 평탄화, seed 의미·저장 ID·지원 배치 앵커·sparse delta 계약 변경을 허용하지 않는다. 가능하면 기존 셀 데이터를 보존한 실제 경사로/표현·콜라이더와 기존 navigation의 연결로 해결한다. 생성 설정의 한정 변경도 기존 저장을 지원할 수 있어야 한다. 현재 저장 계약으로 표현 못 하면 HARD STOP이다.
- 항구↔집↔일터↔상점 사이 NPC의 정상 경로를 실제로 연결한다. Complete 경로와 실제 에이전트 보행·작업·주민 구매·밤 귀가를 확인한다. 화면 밖 Warp/hop으로 이동을 완료한 결과는 경로 연결 PASS가 아니다. 정상 경로를 증명한 뒤에만 해당 우회를 정리한다. 겉으로 가리는 NavMeshLink만 붙이고 절벽 안 통과를 허용하지 않는다.
- 오전 9시 캐릭터 음영/식생, 노을, 밤 상점 창·실내/가격을 같은 정상 카메라에서 확인한다. 실제 모델과 기존 자산을 우선한다. HUD·카메라 구도·수관 가림과 도구/대상 가독성을 함께 맞춘다.

## 4. P9 보완 — 원속에서 읽히는 이동과 도구

기존 PlayerController/CameraController/Animator/입력 권위를 유지한다. 새 캐릭터/리그/컨트롤러를 만들거나 인게임 속도를 몰래 바꾸지 않는다. 기존 사용자 선택 보폭·스타일을 기준으로 clip/blend/transition/접지·그립 표현을 우선 조정한다. 보폭/이동 수치 변경이 꼭 필요하면 이유·변경값·회귀 근거를 남긴다.

idle → walk/run → stop/turn → jump/fall/land, 맨손 및 도끼·곡괭이·낚싯대·잠자리채를 실제 제품 카메라에서 확인한다. 지지발 미끄러짐·지면 파고듦·팔/도구 관통, 양손이 필요한 도구의 그립, 맞는 순간의 타격/SFX/VFX와 보상이 연결돼야 한다. 손가락 뼈가 없는 한계는 숨기지 않는다.

P9 기존 before/after 영상과 evidence부터 읽는다. 같은 경로·카메라·해상도·동작 속도의 연속 비교를 만들고 정면/측면/3/4는 문제 동작에 필요한 만큼 추가한다. 30fps 이상을 목표로 실제 캡처 방식과 벽시계 프레임 성능을 구분한다. `Time.captureFramerate=30` 영상은 고정 simulation-step 자료이며 실시간 30fps 성능 증거가 아니다. 프레임 사진만 보고 모션을 최종 수락하지 않는다.

## 5. 낮 활동·UI·도입·오디오의 남은 연결

Q1~Q6에서 아직 보지 못한 실제 제작 화면, 수납 꺼내기/가득 참, 동행 선택 변경/확정, 가격 취소/고가 반응, 사용한 도구의 드래그/취소/교환 후 내구도 보존을 관련 플레이에 묶는다. 보관된 도구의 내구도를 재실행에도 보존한다고 주장하지 않는다(현재 schema 밖). 이미 완료된 부분 compile/PDB probe/patch 검증은 반복하지 않는다.

직접 Wood/Stone 등 채집 → 원재료 가공/대표 제작 → 필요한 kit/설비 → 실제 상품 진열/가격 → 주민/관광객 구매 → Report로 연결한다. 낮 상품을 fixture로 지급해 이 경로를 대체하지 않는다. 이동/설치 입력은 마우스 위치 지정, E 확정, R 회전, Esc/RMB 취소; 설치 불가·문 앞·벽/가구/NPC·손님 통로와 큰 건물 카메라를 실제 필요한 대표 경우에서 확인한다.

NEW GAME의 교육/가격 인증 → 동료2 선택 → 출항·8~12초 Micro-Cinematic → 섬 도착 → 보급 → 정착과 밤 전환의 소리/화면을 마무리한다. 현재 배/돌섬/전환을 실제로 보고 과거 피드백이 남으면 기존 자산/카메라/Timeline·presentation을 한정 수정한다. QA 직행으로 도입 검수를 건너뛰지 않는다. 실제 오디오 출력/녹음을 확인하지 못하면 코드의 AudioSource 존재만으로 소리 PASS를 기록하지 않는다.

기존 `Logs/CodexParallel/SteamDemoQuality/ReferenceReview-20261005-001/REFERENCE_AUDIT.md`와 로컬 딩컴 영상부터 사용한다. 필요한 동작/화면만 공식 딩컴·Nintendo 자료를 웹에서 관찰한다. 기본은 경험당 대표 1~2개. 검색 제목/설명만으로 영상을 보았다고 하지 않는다. 영상 직접 관찰이 불가능하면 확인된 정적 화면과 미검증 모션을 구분하고 현재 캡처·로컬 자산으로 승인된 보완을 계속한다. 외부 자산/패키지는 내려받거나 가져오지 않는다.

## 제작·사용량·검증 규율

- 한 번에 경험 하나. 관련 수정 묶음 → compile → 영향 검사 → 실제 제품 입력 → GameView → 필요한 수정 순으로 진행한다. 확인되지 않은 원인을 연달아 패치하지 않는다.

- 새 보완 경험의 승인된 Studio 3/3/1 예산을 원인별 기록한다. 과거 P6/P7/P8/P11이 여러 번 실행됐다는 사실을 지우지 않고, 기존 동일 blocker를 새 이름으로 바꿔 무한 재시도하지 않는다. Save/경제/core에는 기본의 엄격한 retry 정책을 적용한다. 소진 시 원인과 정확한 다음 행동을 보존한다.
- 현재 소스·scene·asset에 유효한 기존 PASS는 재사용한다. 변경/실패/미검증의 영향 검사만 한다. 매 수정마다 P1 네 세션, 전체 영업, 모든 validator, Day2~7 장기 검사를 돌리지 않는다. 리스크가 있는 저장/배치/경제 변화의 필수 회귀는 생략하지 않는다.
- 전용 validator·캡처 도구는 기존 것을 우선 사용하며 출력은 고유 폴더로 한다. 기존 증거를 덮어쓰지 않는다. 자동 입력의 포커스/좌표/대상 문제와 제품 결함을 구분한다. 동일 입력 스크립트 실패만으로 제품을 다시 빌드하지 않는다.
- 공유 Editor를 조작하는 작업자는 하나다. 이 실행에서는 추가 작업자를 생성하지 않는다. 관찰 backlog·원칙/스킬 개선·관리 도구를 새 완료 조건으로 붙이지 않는다. 진행 업데이트는 발견·다음 해결을 60초 안팎의 짧은 문장으로 전달한다.

## 최종 P11 — 실제 Windows 납품

수정 묶음이 검증된 뒤 고유 후보를 빌드한다. 최신 후보가 현재 변경에 유효하면 재사용하고, 제품 소스/자산/설정의 관련 변경이 있으면 다시 빌드한다. 기존 candidate4는 인수 기준이며 미래 변경을 자동 포함하지 않는다.

최종 동일 후보에서 다음을 검증한다.

1. 격리 save로 NEW GAME → 교육/가격 → 동료 → 항해 → 섬 → 보급 → **순간이동·재료/돈/진행 주입·시간 가속 없이 실제 보행과 채집/제작** → 정착/Root → 진열/가격 → 자연 노을/밤 → P 개점 → 주민/관광객의 구매/거절 → 자동 마감/Report. 실제 시간과 입력 방식(OS 입력/가상 InputSystem/사람)을 기록한다. 12~15분 목표를 못 맞추면 실제 소요와 이유를 보고한다.
2. 기본 낚시·곤충 성공과 실패/취소·보상, 대표 가공 상품의 판매 연결, 중요한 UI 닫기 후 이동/입력 복귀. 가능하면 위 완주에 묶고 실패/가득 참 등 예외만 targeted로 보완한다.
3. 격리 저장 → 정상 종료 → **새 프로세스** → 타이틀 Continue. 정착 전/완료 후·배치/상자·돈/재고/시간/Root/Report·공급 재지급 방지를 기존 증거와 변경 영향에 맞춰 검증한다. 실제 저장 내용과 복원된 새 객체를 확인한다. 사용자 원본 save는 그대로 둔다.
4. 실제 플레이의 Console/Player 오류, 중요 효과음/밤 분위기, 하드웨어·1920×1080·VSync/FPS 조건·프레임 타임/멈춤. 로딩/scene 전환 긴 프레임을 따로 보여주고 무시하지 않는다. 기존 perf-summary의 구형 후보 결과나 2초 창별 p95를 최종 후보 전체 p95로 취급하지 않는다.
5. 실제 GameView 핵심 화면과 정상 속도 플레이/모션 자료, EXE·관련 player data/DLL의 hash, HEAD+dirty/미커밋 관련 소스·자산 식별, 빌드 결과와 실행 로그를 연결한다. 최신 후보 하나를 지정하고 실행·키·저장·알려진 한계·사람 확인 항목을 짧게 전달한다. 게임 진행을 돕는 안내에는 검사기/fixture 구현 설명을 노출하지 않는다.

기능 PASS / presentation STRUCTURALLY IMPROVED·FAIL·UNVERIFIED / human ACCEPTED·REJECTED·UNVERIFIED를 분리한다. 숫자 PASS로 빈 테스트 맵·발 미끄러짐·가림·무음·과거 사용자 거절을 덮지 않는다. 최종 사람 검수 전에는 전체 데모 RELEASE ACCEPTED를 선언하지 않는다.

기존 approval 안에서 이 보완 순서를 기록하고 한 경험씩 계속한다. `FINAL_WINDOWS_HUMAN_REVIEW`에 도달하면 후보와 증거를 전달하고 멈춘다. 이미 그 milestone이 도달한 상태라면 이번 사용자 시작 메시지에 승인된 보완만 다시 열고, 과거 승인/수락 기록은 보존한다.

## HARD STOP과 기록

원본 save 손실/비호환 migration·새 schema, KEEP 권위 교체/대형 재작성, 무관 dirty 덮어쓰기, 파괴적 Git/파일 작업·삭제, 승인 없는 패키지/자산 다운로드, 새 crash, 동일 blocker 반복/복구 예산 소진, 복구 이후에도 개발 환경 사용 불가는 멈춘다. 필요한 범위를 구체적으로 증명하고 해당 blocker를 한 번 기록한다. 기술적 장애 하나로 계속 가능한 독립 작업까지 완료됐다고 선언하지 않는다.

월별 로그·변경된 현재 문서는 경험 완료 뒤 필요한 부분만 한 번 기록한다. Handoff는 세션 중단/완료 때 한 번 덮어써 현재 티켓·완료/미완료·소진 예산·검증·소스/빌드·정확한 다음 행동을 남긴다. loop-state는 실행 티켓/결과/소유권의 권위이며 별도 큐를 만들지 않는다.

컨텍스트 압축 후에는 완료된 조사/검증을 반복하지 않고 Handoff와 최신 결과에서 재개한다. 사용량 한도로 중단되면 먼저 이 checkpoint를 남긴다. 자동 AI 재호출/무한 실행기나 quota 우회는 만들지 않는다. 실제 도달한 상태만 보고하며 완료 시각·절감률·완벽함을 보장하지 않는다.

공식 지침을 프로젝트에 적용한 부분: 명확한 결과/제약/종료 기준, 승인된 작업의 지속 실행, 로컬 지시 충돌 검수, 변화 영향에 맞는 테스트와 장기 상태 기록. 모델 메뉴에 있으면 GPT-6 Astra High를 기본으로 권장하고 어려운 지형/모션 진단은 XHigh를 선택할 수 있다. 이는 작업 권고이며 프롬프트만으로 모델/노력 설정을 변경하지 않는다. 지속 실행이 필요하면 사용자가 같은 IDE/CLI 세션에서 `/goal`을 선택하고 이 계약의 목표·경계·종료 기준을 사용한다.
