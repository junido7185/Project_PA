# DESIGN_EVENTS — 트렌드 기반 소규모 이벤트 후보

갱신일: 2026-07-17
대상 작업: Task 052
판정: **설계 완료 / 이벤트 시스템·명명 트렌드 코드·이벤트 저장은 미구현**

## 1. 목적과 비범위

이 문서는 Project P.A.에서 실제로 판매한 상품이 다음 날의 마을 경험을 바꾸는 첫 이벤트 후보를 정한다. 이벤트는 상점 운영과 분리된 미니게임이 아니라 다음 루프를 더 선명하게 보여 줘야 한다.

```text
낮 생활 → 재고 준비·가공 선택 → 밤 상점 판매 → 정산 → 다음 날 마을 반응
```

Task 052는 설계 전용이다. 이번 작업에서는 이벤트 컨트롤러, UI, 대사, 씬 오브젝트, 저장 필드, 보상 수치, 구매 규칙을 구현하지 않는다. 실제 구현은 Task 078의 사용자 승인과 선행 작업을 거친 뒤 별도 단일 작업으로 수행한다.

## 2. 현재 프로젝트에서 실제로 사용할 수 있는 기반

### 2.1 구현·검증된 낚시와 판매

- `FishingSpot`은 낮 준비 페이즈에 `shore-forage`의 기존 일일 활동 상태를 사용한다.
- 플레이어는 1.25초 캐스팅 뒤 Fish 2개를 인벤토리에 받으며 같은 날 한 번만 완료할 수 있다.
- `DayNightShopLoopController`는 `DayPreparation → ShopOpen → Settlement`를 소유하고, 정산 뒤 `GameClock.AdvanceToNextDayMorning`으로 다음 날 `OnNewDay`를 발화한다.
- 실제 검증 경로는 Day 2 Fish 2개 획득 → 1개 진열 → 18G 가격 확정 → 밤 개점 → Fisher_01 구매 → 500G에서 518G → Raw `SaleRecord`와 일일 구매 통계 갱신이다.
- 증거: `Logs/Codex_Task041_FishingSaleRoundTrip.log`, `Logs/Codex_Task041_FinalRouteRegression.log`.

### 2.2 이벤트가 읽을 판매 데이터 계약

Task 047의 명명 트렌드 계약을 그대로 사용한다.

| trendId | 허용 판매 쌍 | 현재 상태 |
|---|---|---|
| `trend.fishing` | `(Raw, "Fish")` | 실제 낮 낚시→밤 18G 판매 검증됨 |
| `trend.fishing` | `(Processed, "생선구이")` | Item/Recipe/Kitchen 데이터 존재, 품목별 밤 판매 미검증 |
| `trend.furniture` | `(Luxury, "목제 가구")` | 데이터 존재, 제작→밤 판매 전체 왕복 미검증 |
| `trend.camping` | 없음 | 비활성. 상품·레시피·활동이 없음 |

명명 트렌드는 아직 코드가 아니다. 현재 `VillageChangeSignalController`는 최근 최대 40건을 카테고리별로 읽는 별도 레거시 신호이며, Task 051의 시설 카드는 실제 해금이 아닌 방향 예고다. 이벤트가 이 카테고리 신호를 `trend.fishing`으로 오인하거나 이름 부분 검색으로 Fish를 추론하면 안 된다.

### 2.3 재사용 가능한 기존 소유권

| 관심사 | 기존 소유자 | 이벤트가 지켜야 할 경계 |
|---|---|---|
| 날짜·시간 | `GameClock` | 별도 이벤트 시계 금지. `CurrentDay`, `OnNewDay` 사용 |
| 낮/밤/정산 | `DayNightShopLoopController` | 기존 세 페이즈를 바꾸지 않고 표시와 판정만 덧붙임 |
| 낚시 행동·일일 제한 | `FishingSpot`, `DaytimeStockPrepPoint` | 추가 Fish 지급, 낚시 횟수 우회 금지 |
| 판매 성공 원본 | `ShopSlot` → `SalesLogManager` → `SaleRecord` | 구매 로직·가격 수학 수정 금지. 성공 거래만 읽음 |
| 카테고리 방향 | `VillageChangeSignalController` | 레거시 수식과 시설 예고 보존 |
| 다음 날 문화 변화 | `VillageCultureVisualController` | Processed pending/active 6필드와 이벤트 상태를 합치지 않음 |
| 평판·티어 | `TierService` | 보상은 공개 `AddReputation`만 후보. 승급 규칙 직접 변경 금지 |
| NPC 정체성 | `Profile_Fisher`, `Dialogue_Fisher` | Fisher_01 외형·역할 재매핑 금지. 현재 대사는 Greeting뿐임 |

`SeasonModifier`는 생산량 보정 정적 유틸리티일 뿐 이벤트 일정 시스템이 아니다. 첫 이벤트를 계절 기능으로 가장하거나 기존 생산량을 조정하지 않는다.

## 3. 후보 비교와 선택

| 후보 | 전체 루프 연결 | 현재 데이터 준비 | 위험 | 결정 |
|---|---|---|---|---|
| 해변 풍어제 — 낚시 대회와 밤 장터 | 낚시→Fish/생선구이→밤 판매→다음 날 반응 | Fish 왕복 검증, Fisher 프로필·대사 존재 | 이벤트/명명 트렌드/저장 미구현 | **첫 구현 후보** |
| 새집 꾸미기 목공 장터 | Plank→목제 가구→밤 판매→주민 생활 변화 | 가구 데이터와 B05 존재 | Tier 2, 전체 판매 왕복 미검증 | 두 번째 후보로 보류 |
| 캠핑 소풍 주간 | 캠핑 상품 판매→야외 변화 | 실제 콘텐츠 없음 | 유사 이름 오인·가짜 콘텐츠 생성 | 현재 후보에서 제외 |

첫 이벤트는 `해변 풍어제`로 정한다. 낚시 횟수만 세는 독립 경쟁 미니게임으로 만들지 않고, 낮의 친선 낚시 대회와 밤의 상점 장터를 한 날에 연결한다. 이렇게 해야 “잡은 물고기”가 아니라 **플레이어가 실제로 판 물건이 마을 행사를 만든다**는 핵심 정체성이 남는다.

## 4. 첫 이벤트 계약 — 해변 풍어제

### 4.1 식별과 한 줄 경험

- 설계 ID: `event.fishing.harvest_market`
- 표시명: `해변 풍어제`
- 부제: `낚시 대회와 밤 장터`
- 한 줄 경험: 전날 생선 판매로 마을의 관심을 만든 뒤, 다음 날 낮에 해변에서 낚시하고 밤 상점에서 생선 상품을 판매해 주민과 함께 풍어제를 마무리한다.

### 4.2 잠금 해제 조건

첫 구현의 잠정 기본값은 다음처럼 작고 검증 가능하게 둔다.

```text
settlementDay의 trend.fishing qualifiedTransactions >= 1
AND 해당 일차의 fishing이 선도 명명 트렌드
AND 동일 eventId가 Pending/Active가 아님
AND 최초 이벤트 미완료 또는 재시도 대기 종료
→ 다음 날 해변 풍어제 Pending
```

- 판정 시점은 결제가 아니라 **그날 정산**이다. 판매 순간 화면을 빼앗거나 같은 날 행사를 갑자기 생성하지 않는다.
- `qualifiedTransactions`는 Task 047의 정확한 `(category, itemName)` 매핑과 성공 `SaleRecord`만 센다.
- 첫 검증 기준은 실제 Fish 18G 한 거래이므로 최소 점수는 결과적으로 1018이지만, 이벤트 코드는 가격 18G를 별도 하드코딩하지 않는다.
- 현재 레거시 선도 카테고리와 시설 예고는 잠금 조건이 아니다.
- 실제 구현 전 밸런스 검토에서 거래 기준을 높일 수 있으나, 첫 졸업작품 슬라이스는 1거래로 진입 가능해야 전체 루프를 검증하기 쉽다.

### 4.3 상태 수명주기

| 상태 | 진입 | 플레이어에게 보이는 것 | 종료 |
|---|---|---|---|
| `Locked` | qualifying 판매 없음 | 이벤트 표시 없음 | 정산에서 해금 조건 충족 |
| `Pending` | 정산에서 해금 | 결산에 “내일 해변 풍어제” 한 줄 | 다음 날 `DayPreparation` |
| `Active` | 예정 일차 아침 | 아침 목표, 해변 표식, 밤 판매 대상 안내 | 해당 일차 정산 |
| `ResolvedSuccess` | Active 일차에 qualifying 판매 1건 이상 | 판매 건수·매출·평판 보상 결과 | 다음 날부터 완료 기록 |
| `ResolvedRetry` | Active 일차에 qualifying 판매 0건 | 실패 패널 대신 “다음 기회” 안내, 불이익 없음 | 잠정 3개 완료 일차 뒤 재해금 가능 |
| `Cooldown` | 반복 이벤트 성공 뒤 | 일반 루프로 복귀 | 잠정 7개 완료 일차 뒤 재등장 가능 |

완성형 게임에서는 위 상태가 저장돼야 한다. 같은 세션에서만 유지되는 이벤트를 기능 완성으로 인정하지 않는다.

### 4.4 이벤트 당일 플레이 흐름

#### 아침 — 왜 오늘이 다른지 알림

- `OnNewDay` 뒤 `DayPreparation`에서 기존 목표 카드의 한 구역으로 `해변 풍어제 · 오늘`을 표시한다.
- 목표는 `해변에서 낚시 → 생선 또는 생선구이 준비 → 밤에 상점 판매` 세 단계만 보여 준다.
- Fisher_01은 행사 안내자 후보지만, 현재 `Dialogue_Fisher`에는 Greeting만 있으므로 구현 시 Event 전용 데이터 줄을 명시적으로 추가해야 한다. 기존 대사를 덮어쓰지 않는다.

#### 낮 — 기존 낚시를 행사 행동으로 읽기

- 플레이어는 기존 해변 `FishingSpot`에서 평소와 같은 1.25초 낚시를 한다.
- 성공 시 기존 Fish 2개만 받는다. 이벤트 보너스 Fish, 무한 재낚시, 별도 입력 미니게임은 첫 슬라이스에 넣지 않는다.
- 행사 표식은 기존 낚시터의 위치와 상호작용 면을 가리지 않아야 한다.
- 생선구이를 만들 수 있으면 Kitchen에서 가공하는 선택을 제공하지만, 가공하지 않은 Fish 판매만으로도 완료할 수 있어야 한다.

#### 저녁 — 재고 선택

- Fish는 Raw 18G, 생선구이는 Processed 52G라는 기존 데이터를 그대로 사용한다.
- 이벤트 전용 가격 보정, 강제 구매, 구매 확률 우회는 금지한다.
- 플레이어가 “즉시 팔기” 버튼을 누르는 대신 기존 진열·가격 확정·개점 경로를 거친다.

#### 밤 — 상점이 행사의 결승점

- `ShopOpen`에서 기존 손님이 qualifying 상품을 실제로 구매해야 이벤트 진행이 올라간다.
- 구매 성공 뒤 생성된 `SaleRecord`만 `행사 판매 1건`으로 센다. 진열, 제작, 거절은 0건이다.
- 생선구이와 Fish는 모두 같은 `trend.fishing`에 들어가지만, Raw/Processed 카테고리 신호는 각각 기존 의미로 한 번만 유지된다.

#### 정산 — 결과와 마을 반응

- 결과 카드: `행사 판매 N건 · NG · 구매/보류 통계`.
- 성공 시 기존 판매 수익에 더해 **평판 +1을 한 번만** 주는 것이 첫 보상 후보다. 별도 금화 보너스는 판매 수익과 중복되므로 넣지 않는다.
- 평판 +1은 `TierService.AddReputation(1)` 공개 경로 후보이며, Task 078 승인 때 감사·티어 밸런스 회귀를 반드시 확인한다.
- 영구 시설 해금은 주지 않는다. Task 051 시설 카드는 방향 예고이고 실제 해금은 티어·감사 조건 소유다.
- 시각적 마을 반응은 행사 당일의 임시 해변 장터와 다음 날 짧은 결과 표식까지로 제한한다. 영구 물가 시설은 별도 Task 077/시설 승인이 필요하다.

## 5. 시각·공간·UI 원칙

### 5.1 필요한 최소 시각 세트

- 기존 해변 낚시터와 같은 형태 언어의 낮은 목재 행사 간판
- Fish 바구니와 비어 있는 판매 준비 상판
- 길 찾기와 카메라를 방해하지 않는 천 장식 또는 깃발 한 줄
- Fisher_01의 기존 모델·애니메이션을 유지한 안내 위치
- 아침 목표, 밤 판매 진행, 정산 결과를 같은 크기·여백 체계로 묶은 UI

원시 큐브 조합, 무작위 해양 소품, 출처 불명 생성물, 실제로 쓰지 않는 가짜 도구를 최종 에셋으로 사용하지 않는다. 에셋 제작 전 `Docs/Codex/ART_DIRECTION.md`와 provenance 규칙을 적용한다.

### 5.2 동선 안전선

- 기존 `FishingSpot`의 상호작용 위치와 물가 접근로를 유지한다.
- 행사 오브젝트는 NavMesh와 플레이어 이동을 막지 않으며, 보이는 범위와 Collider가 일치해야 한다.
- Fisher_01 안내 위치는 낚시 트리거, 플레이어 캐스팅 자리, 카메라 초점을 겹치지 않는다.
- 밤 상점에는 새 판매대를 강제 생성하지 않는다. 기존 `ShopSlot`과 현재 배치 시스템을 사용한다.

### 5.3 같은 구도 캡처 체크

실제 구현 시 다음 세 장을 게임 카메라에서 확보한다.

1. 일반 해변일
2. 풍어제 Active 해변일
3. 밤 상점의 행사 상품 판매/정산

각 캡처에서 초점, 스케일, 길 막힘, Collider, 조명, 색상, UI 가독성, 임시 primitive, NPC/플레이어 겹침을 비교한다. 행사 장식이 늘었지만 낚시 위치가 덜 읽힌다면 개선으로 인정하지 않는다.

## 6. 구현 아키텍처 경계

Task 078 승인 뒤에도 기존 시스템을 재작성하지 않는다.

```text
SaleRecord
→ 공용 명명 트렌드 판정기(Task 047 계약)
→ 정산 시 event.fishing.harvest_market Pending 예약
→ GameClock.OnNewDay + DayPreparation에서 Active
→ 기존 FishingSpot/ShopSlot/SalesLog를 관찰
→ 정산에서 성공·재시도 판정
→ UI/임시 월드 프레젠테이션 + 승인된 보상
```

권장 소유권:

- 이벤트는 신규 사이드카 컨트롤러 한 곳이 상태 전이를 소유한다.
- 정확한 상품 매핑과 점수 계산은 공용 명명 트렌드 판정기 한 곳이 소유한다. 이벤트 안에 Fish 문자열 목록을 복제하지 않는다.
- 기존 `FishingSpot`, `ShopSlot`, `PurchaseEvaluator`, `EconomyService`, `NpcController`는 이벤트를 알 필요가 없다.
- 이벤트 표현 계층은 상태를 읽을 뿐 판매·평판·티어 값을 직접 고치지 않는다.
- 메인 씬 YAML을 직접 추측해 수정하지 않고 Unity Editor API/MCP와 런타임 sidecar를 우선한다.

### 6.1 저장 경계

필요한 최소 이벤트 저장 후보:

```text
eventId
state
pendingDay
activeDay
resolvedDay
retryAvailableDay
repeatAvailableDay
activeTransactions
activeRevenue
rewardClaimed
```

- `SalesLogManager` 판매 이력과 Task 047의 향후 7일 `DailyTrendSnapshot`은 Task 054 설계/Task 055 승인 범위다.

## 9. 구현 완료 검증 계약

Task 078은 아래가 모두 확인되기 전 완료가 아니다.

- Raw/Processed 카테고리 신호, 시설 예고, 돈, 누적매출, 구매/보류 통계가 기존 값과 함께 정확하다.

- 실패에는 돈·평판·아이템 손실이 없고 재시도 일차가 명확하다.
- 이벤트 도중 저장 종료/로드, Active 정산, 다음 날 복귀가 같은 상태로 이어진다.
- 일반 Day 1 FinalRoute, 낚시 왕복, Day 1→3 전환, SaveRoundTrip 회귀가 PASS한다.
- 일반 해변/Active 해변/밤 상점의 동일 구도 캡처가 기본 화면보다 동선·초점·가독성을 악화시키지 않는다.
