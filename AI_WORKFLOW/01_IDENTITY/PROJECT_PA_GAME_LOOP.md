# PROJECT_PA_GAME_LOOP — 하루 루프 정의

작성: 2026-07-09
지위: 게임플레이 작업 시 필독. 정체성 상위 문서: `PROJECT_PA_IDENTITY.md`.

## 0. 루프 한눈에

```
[낮] 마을 생활·재료 확보 → [해질녘] 진열·가격·코너 구성 → [밤] 잡화점 영업 → [영업 후] 정산·성장·마을 변화 → 다음 날 계획
```

각 페이즈는 다음 페이즈의 재료를 만든다. 어떤 페이즈도 스킵 가능한 장식이 되면 안 된다.

## 1. 낮 — 마을 생활과 재료 확보

**목적**: 밤 영업의 재료(상품·정보·관계)를 코지한 생활 플레이로 만든다. "걸어가서 직접 한다"는 감각이 핵심.

| 구분 | 내용 |
|---|---|
| 완성 게임에서 필요한 기능 | 채집·낚시·광질·농사 4계열 활동, 주민 의뢰(퀘스트), 마을 꾸미기, NPC 생산자 매입/계약, 가공(워크샵·전문가), 계절/날씨 변화, 시설·구역 확장 |
| 졸업 시연 최소 기능 | 채집 포인트 2곳 이상에서 실제로 걸어가 수집, NPC 생산자 공급 1경로, 인벤토리/핫바 반영 |
| 현재 구현 상태 | 일일 재고 진입 7개: 온보딩/NPC 지원 2개(`garden-basket`, `producer-dropbox`) + 숲길 Carrot, 해변 낚시 Fish, 들판 Wheat, 광산 Ore, 농장 씨앗 주머니. 고정 밭 2칸의 Seed→Wheat3 재배와 전문 주민의 Wheat/Ore/Wood 요청도 구현되어 컴파일·정적 계약 PASS, Unity 실플레이 대기다. Fish 18G와 Ore 15G는 획득→진열→가격→밤 개점→NPC 구매→돈/매출/통계 왕복 완료. 기존 8개 가공 레시피는 Task 091의 결과 수용량 선검사로 재료를 보존하고, Task 103의 C 도감/작업대별 실제 카드·재료/출력·피드백 UI로 플레이어 진입을 연결했다. Task 102는 B09 외부 공동 창고의 24칸 실제 보관/회수 UI를 v10 `storedItems` 경로에 연결했으며 두 UI 모두 실플레이 확인 대기다. 상세: `../03_TASKS/DAYTIME_ACTIVITIES.md` |

## 2. 해질녘 — 진열과 가격 설정

**목적**: 오늘의 수확을 "무엇을, 얼마에, 어떻게 보여줄까"라는 경영 판단으로 바꾼다.

| 구분 | 내용 |
|---|---|
| 완성 게임에서 필요한 기능 | 슬롯별 진열, 가격 설정, 희귀품/일반품 구분 배치, 테마 코너 구성, 수요 예측 정보(스마트폰 앱), 재고/품질 관리 |
| 졸업 시연 최소 기능 | `ShopSlot` 진열 + `ShopPriceUI` 가격 확정 + 상품 2종 이상 선택지 |
| 현재 구현 상태 | 실제 어획 Fish와 실제 채굴 Ore를 포함한 인벤토리 재고의 진열·가격·구매확률 힌트 동작. Fish/Ore는 각각 18G/15G 가격 확정과 밤 판매까지 검증. 별도 rarity 필드 전까지 100G 기본가 경계의 `가격 파생값` 일반/희귀 구분과 실제 품질 배수를 표시한다. `basePrice+quality` 추천 기준가는 읽기 전용이며 플레이어 가격을 자동 변경하지 않는다. 일반/고품질 두 분기 캡처 검증 완료. 테마 코너는 미구현 |

## 3. 밤 — 잡화점 영업

**목적**: 하루의 준비가 손님 반응으로 심판받는 가장 바쁘고 재미있는 시간. 플레이어는 카운터의 호스트다.

| 구분 | 내용 |
|---|---|
| 완성 게임에서 필요한 기능 | 영업 개시/종료 연출, 주민+관광객 2계층 손님, 손님 성향별 반응(구매/거절/흥정), 붐비는 시간대, 진열 보충, 접객 상호작용, 평판·단골 시스템 |
| 졸업 시연 최소 기능 | 밤에만 구매 가능한 영업 게이트, 손님 2타입 이상, 구매/거절 이유가 말풍선으로 읽힘, 돈 변화 즉시 표시 |
| 현재 구현 상태 | 영업 게이트 + NPC 구매판단(`PurchaseEvaluator`, MBTI/가격민감도) + 말풍선 피드백 + 성향 표시 레이어. 실제 마을 일과표가 있는 현재 8명은 말풍선에 `[주민]`, 일과표 없는 향후 방문 손님은 `[관광객]`으로 표시만 파생한다. 낚시→Fish 18G와 광질→Ore 15G가 각각 실제 진열→NPC 구매→돈/누적매출/Raw SalesLog/일일 통계까지 검증 완료. Task 105는 19~20시에 Rest로 전환되던 주민에게 영업 중에만 한시 방문 lease를 부여해 Tier 0 외부·Tier 1 실내의 20~23시 유입을 연결하고 완료·실패·timeout·폐점 뒤 원래 위치·Shop·Rest를 복구한다. Runtime/Editor·정적 계약 PASS, 실제 시간대 플레이 확인 대기 |

## 4. 영업 후 — 정산과 성장, 마을 변화

**목적**: "오늘 판 것"이 "내일의 마을"로 이어지는 것을 보여준다. 핵심 차별점이 증명되는 페이즈.

| 구분 | 내용 |
|---|---|
| 완성 게임에서 필요한 기능 | 일일 정산(매출·카테고리 통계·다음 행동), 가게 확장/시설 해금, 티어/감사 진행, 주민 행동 변화, **판매 카테고리별 마을 풍경 변화**, 저장 |
| 졸업 시연 최소 기능 | 정산 요약 + 다음 목표 표시, 마을 변화 신호 1종 이상 (현재: Processed/Raw/Utility/Luxury 판매 → 다음날 시장 광장 카테고리별 시각 변화) |
| 현재 구현 상태 | Day 정산 + 티어 목표 + `VillageChangeSignalController` + 판매 가능한 4카테고리의 다음날 변화. Processed는 B05 실제 Visual·Project P.A. 준비 키트의 `가공 준비대`, Raw는 CC0 통나무·바위의 `원자재 수거처`, Utility는 철제 도구 Forge 레시피와 연결된 B07 Visual의 `공구 수리대`, Task 108 Luxury는 목제 가구/의류와 연결된 B08 Visual의 `공예 전시대`를 비충돌 시각 전용으로 사용한다. 네 변화는 기존 v10 pending/active category 문자열을 공유하며 Runtime/Editor·정적 계약 PASS, 실제 GameCamera 전후 확인은 안전 캡처 경로 승인 뒤 수행한다. 기록: `Docs/VillageCulture/VC-001A.md` |

Task 109는 성장 지원의 실제 진입도 연결한다. 스마트폰 후보 8명의 빈 전용 프리팹을 이유로 채용이 실패하던 경로를, 같은 전문 분야의 기존 주민 원본 구성과 기존 경제·v10 복원 권위로 안전하게 보완했다. 고용된 전문가는 해당 작업대의 기존 레시피만 받으며 후보별 정체성·친밀도 키와 UI 상태를 표시한다. 컴파일·정적 계약은 PASS했고 실제 채용·역할 행동·저장 복원은 안전 Unity 경로에서 확인 대기다.

Task 110은 이 채용 기능을 첫 주 루프에 배치한다. Day 5 이후 낮 목표와 운영 체크리스트가 미고용 상태에서는 P.A. Phone 채용 행동을 안내하고, 고용 뒤에는 실제 후보 이름·역할·인원수를 완료 상태로 표시한다. Day 7 첫 주 결산도 같은 roster를 보여 주므로 직접 생활 노동→NPC 지원이라는 성장 결과가 주간 기록에 남는다. 채용·비용·스폰·저장 권위는 바꾸지 않았으며 실제 화면 전환은 안전 Unity 경로에서 확인 대기다.

Task 111은 그 지원 인력이 만든 생산물이 실제 플레이어 재고로 들어오는 거래 경계를 복구한다. `Inventory.AddInstance`는 이제 전량 수용을 먼저 검사해 실패 시 기존 슬롯과 전달 스택을 변경하지 않는다. 생산자 NPC는 가방 공간을 결제 전에 확인하고, 가방 가득 참·잔액 부족이면 돈과 NPC 재고를 모두 유지한다. 결제 뒤 예외 실패도 전액 환불하고 상품을 생산자가 보관하며, 성공·보류 이유는 기존 NPC 말풍선으로 표시한다. Runtime/Editor와 30개 정적 거래 계약은 PASS했고 실제 납품 왕복은 안전 Unity 경로에서 확인 대기다.

Task 112는 Day 7 완주 뒤 Day 8부터 일반 반복 문구만 남던 장기 루프를 2주차 캠페인으로 연결한다. Day 8~14는 순서대로 B09 보관, 가공품 판매, 채용, 2카테고리 판매, Tier 1 실내 성장, 다음 날 마을 변화, 2상품 판매를 목표로 삼고 기존 `StorageBox`·`SalesLogManager`·`HiringService`·`TierService`·`VillageCultureVisualController`의 실제 상태를 0.5초 체크리스트에서 읽는다. 자동 온보딩 보급은 Day 7에서 끝나므로 2주차는 직접 채집·생산자 매입·가공·재고 정리로 밤 영업을 준비한다. Runtime/Editor와 40개 정적 계약은 PASS했고 실제 Day 8~14 연속 플레이와 화면 가독성은 안전 Unity 경로에서 확인 대기다.

Task 114는 같은 권위를 Day 15~30까지 확장해 보관·가공·고용·상품 구성·Tier·마을 변화가 순환하는 첫 달 캠페인과 기능적 완주점을 만든다. Day 30 Settlement는 누적 매출·돈·Tier·평판·고용 roster·마을 변화·당일 정산을 요약하고, 저장 뒤 종료하거나 기존 다음 날 권위로 Day 31을 시작해 다시 저장할 수 있다. Day 7 자동 보급/첫 주 완료는 독립적으로 유지되며 새 저장 필드나 퀘스트 시스템은 없다. Runtime/Editor 경고 0·오류 0과 56개 정적 계약은 PASS했고 대표 일차·Day 30 UI·Day 31 실제 왕복은 안전 Unity 경로에서 확인 대기다.

Task 115는 첫 달의 추상적인 Utility/Luxury 목표를 기존 Tier 1 Forge 가치사슬로 정합한다. Tier 1 장부에서 B05와 B07 설계도를 받고, B05에서 Wood→Plank, B07에서 Ore→IronBar→ToolSet을 만든 뒤 Day 23에 철제 도구+다른 상품, Day 24에 철제 도구+Processed를 판매한다. 완료 판정은 활성 B07과 정확한 당일 `Item_12_ToolSet` 판매를 읽으므로 씨앗 Utility만으로 우회할 수 없고, Tier 2/100,000G 전 Luxury 때문에 첫 달이 막히지도 않는다. Day 15~31 매출 표시는 Day 14의 15,000G에서 역행하지 않으며 Tier 데이터·제작·판매·저장 권위는 그대로다. Runtime/Editor 오류 0과 실행 가능 소스 계약 39/39는 PASS했고 실제 배치·제작·판매는 안전 Unity 경로 확인 대기다.

Task 121은 Day 30 완주 뒤 일반 장기 운영 문구로 되돌아가던 구간을 Day 31~45 두 번째 달 진입 캠페인으로 연결한다. 열다섯 날짜는 보관 10/12개, Processed 2/3건, 지원 인력 3명, 상품 3/4종, 기존 Day별 누적 매출 점검선, 활성 B07과 정확한 ToolSet, 3카테고리, 활성 마을 변화, 영업 전 4상품 준비를 실제 상태에서 읽는다. Day 45는 53,500G 점검선과 당일 4상품 판매를 함께 요구하며 Tier 2의 100,000G 조건과 B06 Tier 2 해금은 바꾸지 않는다. 새 퀘스트나 저장 상태 없이 첫 달에 배운 선택을 더 강한 운영 조합으로 반복해 두 번째 달과 Tier 2 장기 성장 사이를 잇는다. Runtime/Editor 오류 0과 계약 23/23은 PASS했고 실제 Day 30→31·대표 상태 전환·화면 가독성은 안전 Unity 경로 확인 대기다.

Task 122는 그 다음 Day 46~76을 Tier 2 성장 캠페인으로 잇는다. Day 46~75는 보관→가공→지원 인력과 영업 전 4상품 준비→3카테고리 판매→활성 B07의 ToolSet+Processed 판매→활성 마을 방향을 고려한 4상품 판매→누적 매출 점검의 7일 리듬을 반복한다. 보관은 12→20개, 가공은 2→4건으로 완만히 상승하며 나머지 권위와 보상은 기존 시스템에 남는다. 기존 목표 수식은 Day 46 55,000G에서 Day 76 100,000G에 정확히 도달하고, `TierService`는 평판·수동 승인 없이 같은 100,000G에서 자동 Tier 2로 승급한다. Day 76은 실제 `CurrentTier >= 2`만 완료로 인정하므로 다음 B06 주방 가치사슬의 기능적 입구가 된다. Runtime/Editor 오류 0과 계약 34/34는 PASS했고 실제 대표 주간 상태·자동 승급·화면 가독성은 안전 Unity 경로 확인 대기다.

Task 123은 Day 77~90을 기존 Tier 2 B06 주방 가치사슬로 연결한다. B06 배치 뒤 Wheat→BreadLoaf, Carrot→구운 감자, Fish→생선구이를 각각 판매하고, 2~3종 메뉴·영업 전 3종 준비·요리사 고용·3카테고리 조합·4개 배치 판매·Processed 마을 변화까지 실제 배치/재고/판매/고용/마을 상태에서 읽는다. Day 90은 활성 B06, 세 주방 상품 판매, Processed 마을 방향을 함께 요구해 재료→조리→상점→마을 변화 루프를 닫는다. Runtime/Editor 오류 0이며 Task 124와 Task 125에서 44개 자동 계약과 B06 Tier 2 switch case·두 Unicode-escaped Item 이름 직접 권위 3개를 합쳐 정적 계약 47/47을 확정했다. Unity 실플레이는 실행하지 않아 `PARTIAL`이다.

Task 126은 Day 91~105를 기존 Tier 3 지역장 성장과 공동 공방 가치사슬로 연결한다. Day 91부터 전문 주민의 실제 낮 재료 요청을 완료하면 기존 일일 활동 저장 목록을 이용해 하루 한 번 평판을 얻고, 평판 3에서 기존 `TierService`가 Tier 3로 자동 승급한다. 이후 기존 B08 재봉 작업대, Wheat2+Plank1→의류, Plank3→목제 가구, 재단사 고용, Luxury 다음 날 마을 변화를 날짜별 목표로 묶는다. Day 105는 Tier 3+B08+의류/가구 당일 판매+Luxury 마을 방향을 함께 요구해 주민 도움→평판→공방→상점→마을 변화 루프를 닫는다. 새 저장 필드·Tier 수치·레시피·아이템·경제식은 없으며 Runtime/Editor 오류 0, 정적 계약 24/24 PASS, Unity 실플레이 대기로 `PARTIAL`이다.

Task 127은 공동 공방의 실제 주민 행동을 기존 GRID 권위에 연결한다. B05~B08의 footprint 바깥 전면 interaction 셀을 전문 주민의 NavMesh 목적지로 사용하고, 완전 경로와 셀 예약을 요구해 작업대 콜라이더 내부 원점으로 이동하거나 주민끼리 같은 자리에 겹치는 문제를 막는다. 작업대 이동·회수와 일정 중단 시 예약과 제작을 해제하고, 저장 상태 복원 뒤에는 현재 배치 기준으로 다시 접근한다. 기존 제작·고용·배치·저장 권위는 그대로 유지하며 Runtime/Editor 오류 0과 정적 계약 29/29를 통과했다. Unity 실제 주민 이동·제작은 사람 판단 게이트로 대기해 `PARTIAL`이다.

Task 128은 밤 영업의 주민+관광객 2계층 중 표시 폴백만 있던 관광객 정상 진입을 연결한다. Day 2+ 개점 중 `CustomerArrivalController`가 스케줄·프로필·실제 SkinnedMesh가 유효한 기존 주민 원본에서 외형만 복제해 런타임 전용 관광객을 만들고, 완전한 NavMesh 외부 진입점에서 기존 `NpcController` 쇼핑 FSM·`PurchaseEvaluator`·말풍선으로 입장→구매/거절→반응→퇴장을 수행한다. 관광객은 주민 일정·생산·전문 역할·대화를 갖지 않고 저장 대상도 아니며, 영업당 2명·동시 1명 상한과 닫힘/시간초과 정리로 주민 영업을 침범하지 않는다. 저장 스키마·구매 수학·씬·프리팹·Day 1 튜토리얼은 유지했고 Runtime/Editor 오류 0, 정적 계약 46/46 PASS다. Unity 실제 왕복과 화면 확인은 사람 판단 게이트로 대기해 `PARTIAL`이다.

Task 129는 Day 106+를 기존 본사 감사와 최종 Tier 4 완주 경로로 연결한다. 기존 정상 플레이 평판은 Tier 2의 3점에서 끝나지만 감사 조건은 평판 5라 최종 등급이 도달 불가능했다. Day 106부터 Tier 3 전문 주민 요청을 완료하면 기존 날짜별 저장 표식으로 감사 요구 평판까지만 하루 1점을 얻고, 목표/체크리스트는 실제 누적 매출 500,000G·평판 5·고용 3명과 다음 정기 감사일을 안내한다. 조건 판정과 수동 승급은 기존 `AuditService`만 수행하며 Tier/감사 수치·저장 스키마는 바꾸지 않는다. Tier 4 통과 뒤 첫 Settlement는 매출·돈·Tier·평판·고용·마을 변화·당일 정산을 담은 전체 캠페인 완주 기록과 저장 후 자유 운영/종료를 제공한다. Runtime/Editor 오류 0, 40개 자동 계약+1개 직접 권위 PASS이며 Unity 실제 감사·완주·저장 왕복 대기로 `PARTIAL`이다.

Task 131은 첨부 GRID/Tripo 정책을 기존 상점 실내·마을 야외 배치 P1~P5와 자산 대장에 다시 고정하고, Day 77~90의 기능적 입구인 B06 Kitchen을 실제 보정한다. Runtime/Editor 오류 0, 정적 계약 30/30 PASS이며 실제 배치·접근·제작·동일 카메라 확인 대기로 `PARTIAL`이다.

## 5. 루프 작업의 우선 규칙

1. 루프의 **연결부**(페이즈 전환, 정산→다음날 반영)가 각 페이즈의 깊이보다 우선한다. 루프가 한 바퀴 안 돌면 아무리 예뻐도 실패.
2. 새 기능은 반드시 "어느 페이즈의 어느 항목인가"를 이 문서 기준으로 선언하고 시작한다.
3. 졸업 시연 최소 기능을 깨뜨리는 변경은 금지. Day 1 루트(`Prototype_FirstDay.unity`)는 항상 통과해야 한다.
4. 완성 게임 기능을 추가할 때도 시연 라인은 보존한다 — 시연은 완성 게임의 부분집합이지 별도 분기가 아니다.
